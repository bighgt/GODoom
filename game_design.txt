================================================================================
TwoPointFive — a Doom-style 2.5D game engine in Go
================================================================================
This file is the living design document for the project. It is kept at the
repo root and updated whenever the design changes — treat it as the source
of truth for *why* the code looks the way it does, not just what it does.

Last updated: 2026-08-27 (Phase 3 in progress: collision, doors, status bar,
sound/music, weapons+projectiles all playable; see section 2)


--------------------------------------------------------------------------------
1. VISION
--------------------------------------------------------------------------------
A game engine, written in Go, that plays like Doom: fake-3D ("2.5D")
first-person movement through levels built from 2D floor plans extruded into
walls, floors and ceilings. It loads the exact WAD file format Doom used, so
any Doom/Doom II/Ultimate Doom IWAD (and most PWADs) can be dropped in and
played. Rendering reaches the screen through the Vulkan API on the GPU (see
section 7 for exactly what runs on the CPU vs. the GPU, and why). Level
traversal, collision, and door logic are all driven by the same BSP tree and
map data id Software's original WAD format carries. The platform target is
Windows first. The codebase is written in an idiomatic-Go realization of
object-oriented design (see section 6).

Non-goals for now: networking/multiplayer, a level editor, non-Windows
platforms, and modding beyond what loading a PWAD naturally gives you.


--------------------------------------------------------------------------------
2. PROJECT STATUS
--------------------------------------------------------------------------------
PHASE 1 — COMPLETE. Window + native WAD file dialog, full WAD/BSP parsing,
a complete Vulkan pipeline standing up and presenting a frame every tick.

PHASE 2 — COMPLETE. A CPU software rasterizer (package raster) renders the
level's walls/flats/textures the way Doom's own engine did — front-to-back
BSP walk, per-column clip-based occlusion, perspective-correct texture
mapping — into a 320x200 RGBA frame; Vulkan uploads and presents that frame
each tick via a minimal textured-triangle "blit" pipeline (see section 7 for
why the split is drawn exactly there). Mouse look (yaw + pitch, shear-based
freelook) and a debug text overlay are both in.

PHASE 3 — IN PROGRESS. Playable, not yet "a game":
  - Player/wall collision with wall-sliding (collision.go) and door-opening
    on Space (doors.go), both reusing shared BSP/level queries.
  - The real Doom status bar (STBAR + digits/face/arms/keys, all the actual
    WAD graphics) — see raster/statusbar.go.
  - Sound effects (DMX PCM via a real audio device) and level music (MUS,
    decoded and streamed to a MIDI synth) — see section 8.
  - Six switchable weapons (keys 1-6) with raise/lower/fire animation timed
    from id's own info.c state tables, each firing a visible projectile
    that flies until it hits a wall — see section 9.
  - No monsters, items, pickups, or real damage yet — Player/ammo/health
    are still static/simplified stand-ins; see section 10 (roadmap) for
    exactly what's still ahead and what's been simplified along the way.

Verified continuously against the real shareware doom1.wad (testdata/) via
`go test ./...` (WAD/BSP/DMX/MUS decoders) and manual play-testing each
feature as it landed.

3. PREREQUISITES / ENVIRONMENT
--------------------------------------------------------------------------------
- Go 1.26+.
- A cgo-capable C compiler on PATH. This project used WinLibs' MinGW-w64
  (POSIX threads, UCRT runtime) build, installed via:
      winget install --id BrechtSanders.WinLibs.POSIX.UCRT
  The GLFW and Vulkan bindings are both cgo packages; without a C compiler,
  `go build` fails at the cgo compile step, not with a helpful Go-level error.
- A Vulkan-capable GPU + driver (vulkan-1.dll present, a real ICD
  registered). The Vulkan SDK (winget: KhronosGroup.VulkanSDK) is needed at
  *build* time too now, for `glslc` to compile render/vulkan/shaders/*.vert
  and *.frag to the *.spv files embedded into the binary via go:embed —
  those .spv files are checked in, so a plain `go build` doesn't need the
  SDK unless a shader source changes.
- Windows, for two reasons: render/vulkan's window-surface path goes
  through GLFW+win32 (portable in principle), but audio/midi_windows.go's
  music playback talks to winmm.dll directly (not portable — see section 8).
- Git, for version control (winget: Git.Git).
- Your own Doom-engine IWAD or PWAD file. None is bundled — see section 4.

4. WAD FILE FORMAT (as implemented in package `wad`)
--------------------------------------------------------------------------------
WAD ("Where's All the Data?") is the single-file archive format Doom (1993)
introduced and every id Tech 1-derived engine since has reused.

IMPORTANT: no WAD file ships with this repo. IWADs (doom.wad, doom2.wad,
...) are id Software's commercial, copyrighted game data. Even the
shareware episode (doom1.wad) — used locally in testdata/ purely to exercise
the parser in automated tests — carries its own historical shareware
distribution terms and is excluded from version control via .gitignore.
Supply your own IWAD, or use a free/open replacement such as Freedoom.

4.1 Header (12 bytes, wad.Header, decoded in wad.Parse): 4-byte ASCII magic
    ("IWAD"/"PWAD"), int32 lump count, int32 directory offset. Little-endian.

4.2 Directory (wad.DirEntry) — one 16-byte entry per lump: int32 file
    offset, int32 size, 8-byte zero-padded ASCII name. Lump lookup is by
    name; where a name repeats (a PWAD overriding an IWAD lump), the *last*
    entry wins — wad.WAD.Find/IndexOf implement that directly.

4.3 Level lumps — a fixed run of lumps immediately following a map marker
    lump (E1M1 style or MAP01 style). wad.WAD.LoadLevel walks forward from
    the marker, decoding each recognized lump until it hits something that
    isn't part of the block:
      THINGS    10 bytes/entry: X, Y int16; Angle, Type, Flags uint16.
      LINEDEFS  14 bytes/entry: StartVertex, EndVertex, Flags, SpecialType,
                SectorTag, FrontSidedef, BackSidedef (uint16;
                wad.NoSidedef=0xFFFF = none).
      SIDEDEFS  30 bytes/entry: XOffset, YOffset int16; Upper/Lower/Middle
                Texture (8-byte names); Sector uint16.
      VERTEXES  4 bytes/entry: X, Y int16.
      SEGS      12 bytes/entry: StartVertex, EndVertex uint16; Angle int16
                (BAM); Linedef uint16; Direction int16 (0 = same direction
                as the linedef, 1 = opposite — this is literally the "side"
                value bsp.SegSides uses); Offset int16.
      SSECTORS  4 bytes/entry: SegCount, FirstSeg uint16.
      NODES     28 bytes/entry: X,Y,DX,DY int16 (partition line); two
                [4]int16 bounding boxes; RightChild, LeftChild uint16 (high
                bit set, wad.SubsectorBit, means "index into SSECTORS").
      SECTORS   26 bytes/entry: FloorHeight, CeilingHeight int16;
                Floor/CeilingTexture (8-byte flat names); LightLevel int16;
                SpecialType, Tag uint16.
      REJECT/BLOCKMAP — raw bytes (wad.Level.Reject/Blockmap); REJECT isn't
                decoded anywhere yet (no monster AI to use it); BLOCKMAP
                isn't either — collision.go brute-forces over all Linedefs
                instead of using it as a spatial index (see section 9's
                note on that).

    BAM ("binary angle measure"): a full turn is the full 16-bit range
    (0..65535); `radians = float64(angle)/65536*2*math.Pi`. Not currently
    used anywhere (Thing.Angle, used for the player start and nothing else
    yet, is in plain degrees, not BAM).

4.4 Graphics lumps (wad/graphics.go, wad/textures.go, wad/dmx.go, wad/mus.go)
      PLAYPAL     — 14 palettes x 256 RGB colors; wad.LoadPlaypal. Every
                    other graphic lump stores palette *indices*.
      COLORMAP    — 34 x 256-byte light-level remap tables; wad.LoadColormap.
                    Decoded but not yet used (no dynamic lighting model).
      "picture format" — column-major, run-length-encoded: 8-byte header
                    (Width, Height uint16; LeftOffset, TopOffset int16),
                    per-column uint32 offsets, then "posts" (topDelta byte,
                    0xFF ends the column; length byte; 1 padding byte;
                    `length` pixel bytes; 1 padding byte). wad.DecodePatch.
                    Used for wall texture patches, the status bar, weapon
                    viewmodels, and (once available) THINGS sprites — every
                    non-flat graphic in the game uses this one format.
      PNAMES/TEXTURE1/TEXTURE2 — composite wall textures: PNAMES is a flat
                    list of patch lump names (wad.LoadPnames); TEXTUREx
                    lumps (wad.LoadTextureDefs) each describe a named
                    texture as a canvas size plus a list of (patch index,
                    x, y) placements, composited by wad.WAD.ComposeTexture
                    (later patches draw over earlier ones, but only where
                    the later patch itself is opaque).
      Flats       — floor/ceiling textures: no header at all, just Size*Size
                    raw palette-index bytes (always 64x64 in vanilla IWADs);
                    wad.DecodeFlat.
      DMX sound (DS* lumps) — wad.DecodeDMX: 8-byte header (uint16 format,
                    must be 3 for PCM; uint16 sample rate, almost always
                    11025 Hz, occasionally 22050; uint32 sample count)
                    followed by that many 8-bit unsigned mono PCM samples.
      MUS music (D_* lumps) — wad.DecodeMus: Paul Radek's MUS format, id's
                    own DMX library's compact MIDI-equivalent format. See
                    section 8 for the full event encoding and how it's
                    played back; wad/mus.go's doc comments carry the
                    byte-level format reference.

4.5 assets.Textures (package `assets`) sits on top of `wad` and is what the
    rest of the engine actually asks for a texture/flat/sprite by name: it
    loads the palette/PNAMES/TEXTUREx tables once, decodes+caches each
    named resource (composite wall texture, flat, or arbitrary "picture
    format" sprite — the last via assets.Textures.Sprite, used for
    everything HUD/weapon-related) on first request, and falls back to a
    magenta/black checkerboard placeholder for a texture *name* that's
    referenced but can't actually be resolved, so a bad reference is
    visibly wrong instead of invisible.

5. BSP TREE DESIGN (package `bsp`)
--------------------------------------------------------------------------------
Doom WADs ship a *precomputed* BSP tree per level (NODES/SSECTORS/SEGS) —
this engine reconstructs the exact tree the WAD already encodes rather than
building one from scratch.

  bsp.Node — an interface (InnerNode: a split, with Right/Left children;
  Leaf: a convex subsector, wrapping a wad.Subsector). bsp.Build walks
  NODES once from its last entry (always the tree's root). bsp.Traverse
  does the classic front-to-back walk (compare the camera point against
  each partition line, InnerNode.Side, recurse near-then-far).

  Two more queries on top of the tree, both added in Phase 3 and shared
  across rendering, collision, and doors:
    bsp.PointSector(tree, level, x, y) — descends the tree to find which
      Sector contains a point; used for the camera's eye height, door
      target-sector resolution, and step-height checks.
    bsp.SegSides(level, seg) — resolves a Seg's front/back Sidedef+Sector,
      honoring which side of its parent Linedef the seg actually runs
      along (Seg.Direction is literally Doom's own "side" value). Used by
      both the renderer (wall/flat texturing) and PointSector.

  Why keep BSP traversal at all, when a real depth buffer would resolve
  occlusion regardless of draw order? Two reasons: it's still how the
  renderer decides *when to stop* (a column fully occluded by a nearer
  wall short-circuits every farther seg at that column, see section 7 —
  no depth buffer involved, since the renderer is CPU software, not GPU
  triangles), and it's exactly the point-location structure collision and
  doors need ("which sector is this point in").

6. OOP PHILOSOPHY
--------------------------------------------------------------------------------
Go has no classes or inheritance, so "the core essential of the engine is
OOP" is realized idiomatically:

  - Encapsulation: unexported decode/implementation details everywhere
    (wad's decodeVertexes etc.; render/vulkan's createXxx sequence; raster's
    per-column clip arrays), exported types/methods only at real seams.

  - Interfaces as contracts at every seam with (or plausibly headed toward)
    more than one implementation: engine.Entity, engine.System,
    render.Renderer (today: render/vulkan.Renderer), bsp.Node. Consumers
    (engine.Game.Run, bsp.Traverse) depend on the interface, not the
    concrete type — the engine's polymorphism.

  - Composition over inheritance: engine.BaseEntity is an embeddable base
    struct (ID/position bookkeeping, a default no-op Update) any concrete
    entity type embeds and "overrides" by defining its own method of the
    same name — Go's answer to a base class, without a class hierarchy.

  - One deliberate, documented exception: render/vulkan.Renderer.New takes
    a concrete *window.Window, not a generic surface interface — Vulkan
    surface creation is fundamentally tied to GLFW's C window handle, and
    there's exactly one windowing backend to abstract over. The
    render.Renderer interface itself (DrawFrame/WaitIdle/Destroy) is still
    what engine.Game holds and calls through, so the OOP boundary that
    actually matters (game logic vs. GPU backend) is real.

  - A second, newer one: engine's collision/door/projectile helpers
    (collision.go, doors.go, projectiles.go) are plain methods on *Game
    operating on shared *wad.Level state, not their own
    interfaces/entities — there's exactly one implementation of each and
    no plausible second one on this project's horizon, so introducing
    interfaces there would be ceremony, not abstraction. engine.System
    still exists as the extension point for when that stops being true
    (e.g. real monster AI).

7. RENDERING APPROACH — CPU RASTER + VULKAN BLIT
--------------------------------------------------------------------------------
This is the one place the design changed from the original Phase 1 plan
(which described building wall/flat geometry as GPU vertex/index buffers).
That plan was abandoned in favor of something that reads as far more
faithful to "operates the same as the original C code" while still
satisfying "rendering is done via a GPU":

  - Package `raster` is a software rasterizer — walls/flats/textures are
    computed on the CPU, one screen column at a time, via a front-to-back
    BSP walk, exactly mirroring id's own architecture (R_RenderBSPNode,
    R_StoreWallRange's per-column clip arrays) rather than reinterpreting
    it as GPU triangles:
      - renderer.go: per-seg screen projection (perspective-correct via
        1/depth interpolation), per-column wall-piece drawing
        (drawWallSpan — texture V stretches/compresses with distance,
        since depth is constant across a column so world-Z is linear in
        screen-Y, see its doc comment) and floor/ceiling filling
        (drawFlatSpan — a per-column floor-casting technique, the
        column-major equivalent of Doom's own per-row visplane spans).
        r.ceilClip/r.floorClip (one int per column) are the exact
        occlusion mechanism id's ceilingclip/floorclip arrays were: once
        a column is fully closed by a nearer solid wall, farther subsectors
        visited later in the same traversal skip it outright.
      - camera.go: Camera{X,Y,Z,Angle,Pitch,FOVDeg}. Pitch (look up/down)
        is the same vertical-shear approximation classic source ports used
        to add freelook without truly rotating the camera in 3D — MaxPitch
        (32°) is where that approximation starts visibly distorting
        floors/ceilings, same as those ports.
      - blit.go: the one shared pixel-copy primitive (with/without honoring
        a sprite's own hotspot offset) every sprite draw in the package —
        status bar, weapon viewmodel — is built on.
      - statusbar.go, weapon.go, hud.go, billboard.go: draw directly into
        the same Pix buffer the 3D view was just rendered into (see below
        for why that's the point).
    InternalWidth/InternalHeight are fixed at 320x200 — vanilla Doom's own
    resolution, chosen deliberately (not just left over from a low-res
    placeholder).

  - render/vulkan is *only* a "blit" pipeline: every frame, DrawFrame
    uploads that 320x200 RGBA buffer into a GPU texture (via a host-visible
    staging buffer + vkCmdCopyBufferToImage, see texture.go/frame.go) and
    draws one fullscreen triangle sampling it (pipeline.go, shaders/blit.*)
    with **linear** filtering (texture.go) — chosen over nearest
    specifically so the GPU's own bilinear sampler smooths the whole
    upscaled frame, HUD text included, instead of leaving it chunky. That
    smoothing is genuinely done in hardware (the sampler), which is why
    HUD text (raster/hud.go) is drawn into the same low-res buffer instead
    of as a separate high-resolution overlay — one sampler ends up smoothing
    everything, 3D view and text alike, with no second pipeline needed.

  This means the "is it GPU-rendered" question has a precise answer: the
  BSP/wall/flat rasterization is CPU work (matching the original engine's
  own architecture, per the user's explicit request to replicate it); the
  texture upload, sampling/filtering, and every pixel that ends up on
  screen going through the swapchain is real GPU work via Vulkan — nothing
  in the presented image is drawn by CPU-side software blitting to the
  window. render/vulkan/device.go's pickPhysicalDevice records which
  physical device was actually selected (Renderer.DeviceName/
  DeviceTypeName/DeviceIsSoftware) specifically so this can be verified
  at runtime rather than just asserted structurally — cmd/engine/main.go
  logs it and warns loudly if DeviceIsSoftware ever comes back true
  (a CPU/software Vulkan implementation, which would mean *no* GPU
  hardware is actually involved).

  Known limitation, deferred rather than built speculatively: window
  resize/minimize isn't handled (DrawFrame errors on
  VK_ERROR_OUT_OF_DATE_KHR instead of recreating the swapchain);
  swapchain.go's destroySwapchain is already split out for when that's added.
  A second: sprite billboards (raster/billboard.go, used for weapon
  projectiles) draw on top of everything with no depth test against the
  walls already rasterized — real per-pixel sprite occlusion needs either
  a depth buffer or per-column depth tracking, neither of which exist yet
  (see section 10, Phase 4).

8. SOUND (package `audio`, wad/dmx.go, wad/mus.go)
--------------------------------------------------------------------------------
Mirrors vanilla Doom's own split between two unrelated audio systems rather
than unifying them, because id's original engine didn't:

  - Sound effects: audio.Device wraps a single github.com/ebitengine/oto/v3
    Context (11025 Hz, mono, 8-bit unsigned — matching the overwhelming
    majority of DMX sound lumps exactly, so most sounds need zero format
    conversion; the rare 22050 Hz sound is nearest-neighbor resampled,
    audio.resample). Device.PlaySound is fire-and-forget — oto's own mixer
    keeps a playing Player alive without this package retaining a
    reference, the standard pattern for one-shot oto sounds. Triggered
    today by door open/close (DSDOROPN/DSDORCLS, doors.go) and weapon fire
    (each WeaponDef's own FireSound, weapons.go); engine.Game.playSound/
    loadSound (sound.go) decode-and-cache by lump name so a repeated sound
    doesn't re-parse its lump every time.

  - Music: wad.DecodeMus parses a D_* lump's MUS event stream — id's own
    Paul-Radek-authored compact MIDI-equivalent format (see wad/mus.go's
    doc comments for the exact event-byte bit layout, delta-time VLQ
    encoding, and the MUS-to-MIDI controller mapping table, all verified
    against real event counts/durations in wad/sound_test.go) — into a
    flat []wad.MusEvent (already translated to MIDI channel/note/CC terms,
    MUS's dedicated percussion channel 15 remapped to General MIDI's
    channel 9). audio.MusicPlayer (audio/midi_windows.go) streams those
    events to Windows' winmm.dll MIDI output (MIDI_MAPPER, i.e. whatever
    synth Windows has configured — normally the built-in Microsoft GS
    Wavetable Synth) in a background goroutine, timed against MUS's
    assumed-default tempo (120 BPM at 70 ticks/quarter-note, since a MUS
    lump carries no tempo meta-event of its own) with drift-free absolute
    scheduling. This is Windows-only and deliberately so — see section 3;
    audio/midi_other.go is a no-op stub on other platforms so the rest of
    the engine still builds/runs (sound effects, which don't depend on
    winmm, are unaffected). cmd/engine/main.go looks up "D_"+mapName and
    starts it looping; Doom II's non-obvious per-map music names
    (D_RUNNIN, D_STALKS, ...) aren't in a lookup table yet, so only
    E1Mx-style WADs (and any PWAD that happens to name its music lump to
    match its map) get music today.

  A subtle correctness point worth keeping in mind if this code is ever
  touched again: MusicPlayer.Play/Stop both wait for the *previous*
  player goroutine to fully exit (via a doneCh close) before touching the
  shared MIDI handle again — an earlier version raced Stop's
  midiOutClose against the goroutine's own final "all notes off" cleanup
  and crashed with an access violation calling into the closed handle.

9. GAMEPLAY SYSTEMS (package `engine`)
--------------------------------------------------------------------------------
engine.Game owns the window, the render.Renderer, the raster.Renderer, the
loaded WAD/Level/BSP tree, the Camera, PlayerStats, WeaponState, audio
device/music player, and every live Entity/System. Game.Run is the main
loop: poll input, move the camera, handle the use-key/weapon-keys/fire,
update doors and projectiles, run Systems/Entities, rasterize a frame,
draw the weapon viewmodel + status bar + optional debug HUD text on top of
it, present via the GPU renderer.

9.1 Collision (collision.go) — the player is a playerRadius=16 (id's own
    PLAYERRADIUS) circle; tryMove attempts a full 2D move and, if blocked,
    retries X-only then Y-only (a simple approximation of Doom's own
    axis-separated P_TryMove, enough to slide along non-axis-aligned
    walls). anyLineWithin/wallOpeningAt are the shared "is there a wall
    within radius of this point, and if it's two-sided what's the vertical
    gap" query both this and projectile flight (9.3) are built on: a
    one-sided line always blocks; a two-sided line blocks the player if
    the opening is shorter than playerHeight=56 (id's thing-height
    constant) or the step up from the current floor exceeds
    maxStepUp=24 (id's STEPSIZE). This is a brute-force scan over every
    Linedef, not the WAD's own BLOCKMAP spatial index — fine at this
    project's map sizes (a few hundred lines), but the obvious first
    optimization if that ever stops being true.

9.2 Doors (doors.go) — Space is the "use" key: tryUseDoor casts a ray
    (rayIntersectsSegment) from the camera along its facing direction,
    finds the nearest Linedef within useRange=64 (id's USERANGE) whose
    SpecialType is a supported manual door special (manualDoorSpecials:
    1/26/27/28/117 = DR, open-wait-close, repeatable; 31/32/33/34/118 = D1,
    open-and-stay), and activates it. Only the *manual* door family bound
    directly to the used line is supported — not the tag-based
    remote-trigger families (types 2/3/4/16/...) that move a different,
    tagged sector; keycard-locked variants are treated as unlocked (no key
    inventory yet). A doorThinker per moving Sector animates its
    CeilingHeight between closed and P_FindLowestCeilingSurrounding-4
    (lowestAdjacentCeiling) at doorSpeed=70 units/sec (id's VDOORSPEED,
    2 units/tic * 35 tics/sec) with a doorWaitSeconds=150/35 pause (id's
    VDOORWAIT) before auto-closing. Critically, the animated height is
    written straight into the shared g.Level.Sectors slice — the same one
    the renderer and collision code read every frame — so an opening door
    is immediately visible and immediately walkable through with no extra
    plumbing between the three systems.

9.3 Status bar (raster/statusbar.go) — draws the actual STBAR background
    and STTNUM/STYSNUM/STGNUM/STFST/STKEYS graphics at the exact pixel
    positions id's own st_stuff.c used (ST_HEALTHX/Y=90,171;
    ST_ARMORX/Y=221,171; ST_AMMOX/Y=44,171; ST_FACESX/Y=143,168;
    ST_ARMSBGX/Y=104,168 with a 3x2 grid at 12x10 px spacing; small ammo
    rows at y=173/179/185/191; keys at x=239, y=171/181/191) against a
    raster.PlayerStats that's currently a fixed/simplified stand-in (see
    section 10) rather than real tracked player state.

9.4 Weapons (weapons.go, raster/weapon.go) — six switchable weapons, keys
    1-6 (Pistol, Shotgun, Chaingun, Rocket Launcher, Plasma Rifle, BFG9000
    — vanilla's fist/chainsaw key-1 slot isn't counted among these, a
    deliberate deviation from the 7-slot original per how this project was
    asked to key them). Each WeaponDef.FireFrames/FlashFrames is ported
    directly from id's own info.c states[] table (see the source comments
    in weapons.go for the exact per-weapon frame-letter/tics data, and
    which minor simplifications were made: two weapons' flash frame is
    chosen randomly between two near-identical variants in vanilla — this
    project always uses the first; a few instant "tics=0" passthrough
    states are just omitted since they draw nothing). frameAt walks a
    frame list's cumulative tic durations against WeaponState's
    fireElapsedTics to find which frame is active, exactly mirroring how
    a chain of id's named states with per-state tic counts behaves,
    flattened into data instead of a state-machine of function pointers.
    Raise/lower speed (weaponRaiseSpeed) is id's own RAISESPEED/LOWERSPEED
    (96 units of psprite travel at 6 units/tic = 16 tics), not invented
    tuning. SwitchWeapon marks the target slot "owned" in the arms widget
    immediately (Player.Weapons[index+2]=true) — this project's stand-in
    for a real pickup system not existing yet, so switching to a weapon is
    what makes its status-bar digit light up.

9.5 Projectiles (projectiles.go, raster/billboard.go) — FireWeapon spawns
    one Projectile per shot along the camera's full 3D aim direction
    (aimDirection combines yaw and pitch, so looking up/down with
    mouselook genuinely changes a shot's trajectory) at
    projectileSpeed=1000 units/sec; updateProjectiles advances it each
    frame and kills it via the same wallOpeningAt query collision uses
    (projectileHitsWall) — a one-sided line always blocks it, a two-sided
    line blocks it only if there's no vertical opening at all (no
    step-height tolerance, unlike the player: a shot either has a way
    through or it doesn't). There's exactly one projectile "kind" for all
    six weapons right now — a real rocket, plasma bolt, and hitscan bullet
    all behave identically (a visible orange-yellow marker,
    raster.DrawBillboard, flying in a straight line) — see section 10 for
    the more authentic split (instant hitscan vs. true traveling
    projectile, per weapon) this is standing in for.


--------------------------------------------------------------------------------
10. ROADMAP
--------------------------------------------------------------------------------
Near-term, filling in Phase 3's remaining simplifications:
  - Real player state: health/armor/ammo that actually change (damage,
    pickups, ammo consumption already deducts on fire but nothing ever
    refills it), replacing raster.DefaultPlayerStats' fixed loadout.
  - Hitscan vs. true projectile weapons: pistol/shotgun/chaingun as
    instant hitscans (no travel time), rocket/plasma/BFG as the traveling
    projectiles they already are — today all six behave like the latter.
  - Depth-tested sprite rendering (a real depth buffer or per-column depth
    tracking) so projectiles/things draw correctly behind nearer walls.
  - BLOCKMAP-based spatial indexing for collision instead of the current
    brute-force per-Linedef scan, once map sizes make that worth it.
  - Tag-based remote-trigger line specials (switches/walkover triggers
    that move a different sector than the one activated), not just doors
    bound directly to their own line.
  - Doom II music-lump-name lookup table (D_RUNNIN etc.) so non-E1Mx WADs
    get music too.

Phase 4 — Things: sprites, monsters, items
  - Sprite lump decoding and proper (depth-tested) billboard rendering for
    every wad.Thing, not just projectiles.
  - engine.Entity implementations (Monster, Item, Pickup) built on
    engine.BaseEntity; simple monster AI as engine.System(s), using
    REJECT (decoded but unused today) for line-of-sight fast-reject.

Phase 5 — Polish
  - Swapchain recreation on window resize/minimize.
  - Dynamic lighting via COLORMAP (decoded but unused today).
  - Positional/attenuated sound (currently every sound plays at full,
    unpositioned volume regardless of distance).

Longer-term / explicitly out of scope: networking, a level editor,
non-Windows platform support (music specifically — see section 8), and
Hexen/UDMF map format variants (this engine only targets vanilla-format
Doom levels, checked via the presence of NODES/SSECTORS in LoadLevel).

A note on package github.com/goki/vulkan specifically, because it cost real
debugging time to discover: its generated struct wrappers pass Go strings
to C as a raw, zero-copy pointer into the Go string's own backing array —
NOT a freshly-allocated, C.CString-style null-terminated copy. Every string
handed to a Vk*CreateInfo field must already end in a NUL byte or the C
side reads past the end of the Go string looking for one. render/vulkan/
util.go's nz/nzAll helpers exist purely so this requirement is visible and
hard to forget at each call site.
