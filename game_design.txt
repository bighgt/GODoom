TwoPointFive — Design & Architecture Reference
================================================
What the engine does, in present tense. Rationale for how something got
here lives in git history, not this file.


1. OVERVIEW
-----------
TwoPointFive is a Go engine that plays real Doom / Doom II WAD files as a
first-person shooter, in the architectural spirit of id Software's 1993
engine. The level's own precomputed BSP tree is walked on the CPU
front-to-back into a flat, per-texture-grouped triangle list
(render/worldgeo), and a Vulkan hardware renderer (render/vulkan) does the
actual rasterizing, texturing, depth-testing and shading on the GPU — the
"software rasterizer" this project started from has been fully replaced by
this GPU-geometry path; there is no CPU fallback.

Lighting is entirely the GPU's job: world.frag computes a continuous
version of vanilla's sector/distance fade as the base, then adds dynamic
coloured point lights (map torches and lamps, animated-light sectors, the
weapon muzzle flash, in-flight rockets/plasma/BFG, explosions), the head-
mounted flashlight's spot cone, screen-space shadows and ambient occlusion
for the nearby geometry, a floor contact-shadow blob under things, water/
lava/nukage shading with real screen-space reflections, HDR, bloom, FXAA,
sharpening and an optional cel-shaded "cartoon" look. A global lightScale
(config) dims or brightens the whole map; the default is deliberately
moodier than id's.

The engine ships no game data. A pre-game launcher (section 22) picks the
WAD and level and edits every setting: the freely redistributable shareware
DOOM1.WAD, a retail IWAD, or a PWAD (merged with a base IWAD automatically
— section 2). A companion executable, cmd/isoengine, renders the same
simulation as a top-down isometric game (section 23). A second companion,
cmd/editor, is a dual 2D/3D level editor built on this same stack — it
renders a map's live geometry through the same hardware (GPU-geometry)
renderer the game uses, and saves a PWAD the engine loads straight back
(section 25).

Module `twopointfive`, Go 1.26. Windows and Linux (X11, RADV/Mesa) are both
exercised; macOS is untested. Only the MUS/MIDI music path is Windows-
specific in code (a silent no-op elsewhere), and the startup file picker
has a per-OS backend (sections 13, 16, 21).


2. BUILD & RUN
---------------
Prerequisites:
  - A cgo-capable C toolchain — GLFW and the Vulkan bindings need cgo.
    Built against MinGW-w64 / UCRT64 on Windows; a fresh shell needs
    CGO_ENABLED=1 and the toolchain's bin on PATH.
  - A Vulkan-capable GPU/driver at runtime (vulkan-1.dll on Windows).
  - The Vulkan SDK only to recompile shaders (render/vulkan/shaders/*.vert,
    *.frag -> *.spv via glslc). The .spv files are committed and embedded,
    so an ordinary build never touches it.

From the repo root:
    go build ./...
    go vet ./...
    go test ./...                     (needs cgo — engine imports window/audio)
    go build -ldflags="-s -w" -o bin\engine.exe ./cmd/engine
    go build -ldflags="-s -w" -o bin\isoengine.exe ./cmd/isoengine
    bin\engine.exe

Two commands share the tree: cmd/engine is the first-person game (this
document's default subject); cmd/isoengine is a standalone isometric
top-down mode over the same engine.Game simulation (section 23). Both wire
their process entry point — audio setup, the launcher loop, one play
session — through the same helper shape, de-duplicated between them.

`-ldflags="-s -w"` strips the symbol table and DWARF: harmless for a
release build, roughly halves the binary. Section 18 has the size picture.

Running the engine opens the pre-game launcher (package launcher, section
22): a small fixed-size window — its own GLFW window and a plain
vulkan.New(...) blit renderer, both torn down before the game's own window
opens (launcher.Run) — with a WAD quick-pick list (every *.wad beside the
discovered wad/ directory, launcher.ListWADs), a "Browse..." button (the
OS-native file-open dialog, window.PickWADFile), a level dropdown, and a
scrolling editor for every config.json setting. Play loads the chosen
level; Quit (or closing the window) exits. The launcher does the WAD load +
IWAD merge itself (wad.LoadWithIWAD) to build its map list, and on Play
writes the edited settings — plus the chosen WAD path (config key wadPath)
and map — back to config.json (config.SaveMerge) before handing back a
launcher.Result for cmd/engine to run.

cmd/engine then loops the launcher and a play session: ending a session
(Escape, or the game window's close button) returns to the launcher rather
than exiting the process, so picking another WAD/level or changing a
setting never means relaunching the exe. Only Quit in the launcher (or
closing its window) ends the process.

The launcher is skipped entirely when a WAD path is given up front — a
*.wad command-line argument or $TPF_WAD (window.WADFromCommandLine). That
"headless" route (cmd/engine's runHeadless) is the pre-launcher flow, kept
for scripts, the package's own tests and ad-hoc diagnostics: it loads the
WAD directly and, for a multi-map WAD, picks the start level via
chooseStartMap —
  - config "map" key names one -> start there, no prompt;
  - launched from a terminal -> a numbered console menu on stdin (a number,
    a map name, or Enter for the conventional first level);
  - launched with NO console (stdin is /dev/null, detected by
    window.StdinInteractive via a TIOCGWINSZ ioctl) -> a graphical list
    dialog of every map (window.PickMap, zenity --list / kdialog --menu;
    Cancel or no desktop session -> the default);
  - input already queued on a non-tty stdin (`printf MAP07 | engine`, test
    harnesses) is honoured before either dialog.
The conventional first level (wad.PreferredStartMap) is E1M1 for Doom /
Ultimate Doom-format, MAP01 for Doom II-format, else the first marker. A
single-map WAD always skips straight to it.
Either way, the game then opens borderless fullscreen on the primary
monitor and that level starts.

The pick may be a standalone IWAD or a PWAD. A PWAD (magic "PWAD", or any
WAD with no PLAYPAL) carries only the mod's own lumps, so the loader
(wad.LoadWithIWAD, wrapping wad.Merge — used by both the launcher and the
headless path) finds a base IWAD and merges the two, load order
IWAD-then-PWAD, exactly like Doom's -file. The base IWAD is located by: the
`iwad` config
key if set; otherwise a format guess from the PWAD's map names (E#M# ->
Doom, MAPxx -> Doom II) followed by a scan for the stock IWAD filenames
(DOOM.WAD / DOOM2.WAD / TNT.WAD / PLUTONIA.WAD / freedoom*, any case)
beside the PWAD, up its parent directories, in the working directory, and
beside the exe — each also checked under wad/, wads/, IWADs/, iwads/ and
testdata/. If none is found the game exits with an error naming the `iwad`
key.

Exit: pressing Escape asks the window to close; the game loop returns
cleanly and that session's renderer and window tear down, then cmd/engine
shows the launcher again (the loop above) — Quit there is what actually
ends the process. On process exit, if it owns its console (double-clicked,
so Windows spawned a console that would vanish with it),
window.HoldConsoleOpen prints a prompt and waits for Enter so the debug log
stays readable (cmd/engine/exitpause_windows.go). Launched from a shell,
the console outlives the process and there is no pause. TPF_NO_PAUSE=1
skips the wait unconditionally; off Windows the whole thing is a no-op.

An optional config.json (working directory first, then next to the exe and
up its parents) tunes render resolution, window mode, FOV, lighting, input
and a few gameplay knobs — section 17. The baked-in defaults run fine with
no file. The Vulkan validation layers are a separate env-only switch,
TPF_VK_DEBUG=1, off by default.

The exe expects an `assets/` folder (assets/skybox/, assets/textures/,
assets/voxel/, assets/weapons/ — sections 10, 11, 20). It looks relative
to the working directory first, then relative to the executable's own
directory and up to four parents of it — so bin\engine.exe finds the
repo's assets/ whether launched from the repo root or from bin\
(findAssetDir). Missing is fine: the game runs normally, just without the
upscaled sky, hi-res textures, voxel models and HD weapons (falling back to
the WAD's own data), and each loader logs which it did. Loading from disk
rather than embedding is deliberate — section 18.

  Regenerate the skybox:            go run ./tools/gensky
  Regenerate the hi-res textures:   go run ./tools/gentex
  Inspect a WAD:                    go run ./tools/waddump <file.wad> [MAP]
  Write a complete config.json:     go run ./tools/genconfig [-f]

4. ARCHITECTURE & DATA FLOW
-----------------------------
cmd/engine's run() loop, once per launcher visit (audio.Setup ran first,
process-wide):
    launcher.Run(config.Load())          section 22 — the pre-game menu:
                                          its own window + blit renderer,
                                          wad.LoadWithIWAD (parse + PWAD
                                          merge), map choice, then on Play
                                          config.SaveMerge writes config.json
                                          and it returns a launcher.Result
                                          {WAD, WADPath, MapName, Config}
      -> playSession(res...)             one game session; its defers tear
                                          down every window/GPU/CPU resource
                                          when it returns (Escape / close ->
                                          back to launcher.Run)

playSession(path, mapName, cfg, wad, dev, music):
      -> wad.LoadLevel(mapName)           assemble one map's lumps
      -> bsp.Build(level)                 reconstruct the BSP tree
      -> assets.New(wad)                  palette + texture/flat/sprite resolver
      -> window.New(w,h,title,fullscreen) open the GLFW/Vulkan window
      -> raster.New(textures, rw, rh)     the 2D overlay compositor, at the
                                          resolved render resolution
      -> vulkan.NewWorld(...)             GPU instance/device/swapchain/
                                          pipeline for the hardware
                                          (GPU-geometry) path — the only
                                          renderer; a failed init is fatal
      -> engine.NewGame(...)              wire it into a Game
      -> game.WorldBuilder = worldgeo.New(level, tree, textures)
      -> assets.LoadVoxelPackDir(...)     Doom1/Doom2 voxel models, optional
      -> game.Run()                       main loop until the window closes;
                                          each startup stage is timed
                                          (stageTimer) so a slow load is
                                          diagnosable rather than "hung"

The headless path ($TPF_WAD / a *.wad argument) skips the launcher:
runHeadless does the config.Load + wad.LoadWithIWAD + chooseStartMap itself
and calls the same playSession. cmd/isoengine (section 23) mirrors this
whole structure — same launcher, same playSession shape — with its own
window, its own vulkan.NewIso renderer, and IsoMovementSystem/IsoUseSystem
swapped into the Game.

Per frame, engine.Game.Run (a short loop over pollInput / stepSimulation /
updateFPS / renderFrame / capFrameRate):
  1. compute dt, clamp it to maxFrameDelta (0.1 s); poll OS events (Escape
     asks the window to close, logged once).
  2. run every registered System in order — movement (momentum + collision
     + the vertical fall arc + jump on Space), use (E: doors, switches,
     exits), combat (weapon switch/fire, viewmodel animation, projectiles).
  3. step the fixed 35 Hz simulation: advance every Mobj, the sector
     movers/light animations, animated flats and wall textures, pickups —
     as many whole tics as dt has banked, capped at maxTicsPerFrame — then
     service a pending level exit.
  4. fold the frame rate into an EMA for the debug HUD; advance
     g.renderClock by dt (the free-running seconds value the water ripple
     animates against — worldgeo.Camera.Time).
  5. build and present: the weapon viewmodel, status bar and optional
     debug HUD draw into raster's 2D overlay plane (raster.Renderer never
     touches the 3D world or Vulkan at all any more). Meanwhile
     WorldBuilder walks the BSP into a triangle list (rebuilt only when a
     door/lift moves a sector height or an animated texture steps a
     frame), the frame's map objects/projectiles are collected as sprite
     billboards or voxel instances, this frame's dynamic lights are
     gathered (collectLights), and render.Renderer.DrawWorld hands all of
     it — the triangle list, the camera, the overlay plane, the lights —
     to the GPU, which rasterizes, textures, shades and presents it in one
     pass.
  6. optionally sleep out the rest of the frame budget (only when config
     maxFPS > 0).

raster.Renderer and render/vulkan are deliberately separate concerns:
raster never touches Vulkan or the 3D world, and render/vulkan never sees
a BSP tree or a Sector directly — only the worldgeo triangle list, a
camera, a plain []render.Light, and raster's finished overlay plane to
blend on top.


5. PACKAGE wad — THE WAD FILE FORMAT
--------------------------------------
A WAD ("Where's All the Data?") is id's single-file archive for
Doom-engine games.

Header (12 bytes): 4-byte magic ("IWAD" a whole game, "PWAD" a patch
loaded alongside one), int32 lump count, int32 directory offset.

Directory: one 16-byte entry per lump — int32 offset, int32 size, 8-byte
zero-padded ASCII name. Lookup is case-insensitive; if a name repeats the
LAST entry wins (wad.WAD.Find / IndexOf), which is how Doom's own
patch/override system works.

wad.Merge(base, patches...) concatenates several loaded WADs into one in
load order: it copies every backing buffer into one fresh slice, re-bases
each later WAD's lump offsets, and rebuilds the name index so Find /
IndexOf keep last-wins semantics across the whole set. cmd/engine uses it
to graft a PWAD onto its base IWAD (section 2). ListMaps collapses a map
marker present in more than one merged WAD to a single entry.

Level lumps — a fixed sequence after a map marker ("E1M1", "MAP01"), read
until a lump that doesn't belong:
  VERTEXES   4 B/entry: int16 x, y
  LINEDEFS  14 B/entry: start/end vertex (uint16), flags, special type,
            sector tag, front/back sidedef (uint16, 0xFFFF = none)
  SIDEDEFS  30 B/entry: x/y texture offset (int16), upper/lower/middle
            texture name (8 B each), sector index (uint16)
  SECTORS   26 B/entry: floor/ceiling height (int16), floor/ceiling flat
            name (8 B each), light level (int16), special, tag
  THINGS    10 B/entry: x, y (int16), angle (uint16), type, flags
  SEGS      12 B/entry: start/end vertex (uint16), a BAM angle at offset 4
            (skipped — the renderer takes seg orientation from the
            vertices), linedef (uint16), direction (0 = same winding as the
            linedef, 1 = opposite), offset (int16)
  SSECTORS   4 B/entry: seg count (uint16), first seg index (uint16)
  NODES     28 B/entry: partition line (x,y,dx,dy int16), a bounding box
            per child at offsets 8..24 (skipped — bsp.Traverse walks
            front-to-back with no bbox reject), two uint16 child indices —
            bit 15 set marks a leaf (index into SSECTORS), clear an inner
            node; see wad.SubsectorBit
  REJECT    sector-pair visibility bits — kept out of wad.Level entirely;
            sight traces run the geometry directly (sight.go)
  BLOCKMAP  the WAD's own spatial hash — likewise dropped; the engine
            builds its own collision grid over the Linedef data
            (sections 14, 18)

Global lumps:
  PLAYPAL   14 palettes x 256 colours x 3 B (RGB). wad.LoadPlaypal.
  COLORMAP  34 light-level shading tables, 256 B each — NOT read: the
            renderer reproduces their effect directly in RGB (sections 8,
            16), so there is nothing to decode.
  PNAMES    patch-name list; TEXTURE1/TEXTURE2 index into it
  TEXTURE1/2  composite wall-texture definitions — a canvas size plus a
            list of named patches stamped on, later over earlier but only
            where opaque (wad.WAD.ComposeTexture)
  DS*       sound effects, DMX PCM: 8-byte header (format, sample rate,
            sample count) + that many 8-bit unsigned samples, almost always
            11025 Hz (wad.dmx.go)
  D_*       level music, Paul Radek's MUS format — a MIDI-like event
            stream; wad.DecodeMus translates it to near-1:1 MIDI terms

Graphic formats:
  "Picture" (wall patches, sprites, UI graphics): 8-byte header (width,
  height, left/top offset) + a per-column post-offset array + run-length
  opaque "posts" per column, everything else transparent. wad.DecodePatch.
  Flats (floor/ceiling): no header — exactly Size*Size raw palette-index
  bytes, always square (64x64 in every vanilla IWAD). wad.DecodeFlat.


6. PACKAGE bsp — BINARY SPACE PARTITIONING
-------------------------------------------
Every vanilla-format level ships its BSP tree precomputed in its own WAD
data (NODES / SSECTORS / SEGS). This engine reconstructs that tree rather
than building one (bsp.Build), turning the flat NODES array into an object
graph:
  bsp.Node       interface — an *InnerNode or a *Leaf
  bsp.InnerNode  a partition line (X,Y,DX,DY) + Right/Left child subtrees
  bsp.Leaf       a convex subsector: one or more Segs, all in one Sector

bsp.Build validates as it recurses: every child index is bounds-checked,
and a per-node "seen" set rejects a NODES lump whose child pointers form a
cycle or a DAG — a corrupt or hostile user WAD — with an error rather than
recursing until the stack overflows.

bsp.Traverse walks the tree front-to-back relative to a given (x,y): at
each split, visit the near side first — the same draw-order algorithm the
original renderer used, and what collision and point-location build on too.

bsp.PointSector(tree, level, x, y) answers "which Sector contains this map
point": descend via InnerNode.Side to a Leaf, then resolve that leaf's
first Seg to its front Sidedef's Sector via bsp.SegSides. Used every frame
for camera eye-height, and by movement/door code for arbitrary-point floor
lookups.

bsp.SegSides(level, seg) resolves a Seg's front/back Sidedef and Sector,
honouring seg.Direction — the one shared lookup the renderer and
PointSector both build on.


7. PACKAGE assets — TEXTURES, FLATS, SPRITES, SKYBOX
----------------------------------------------------
assets.Textures (built once per WAD by assets.New) resolves named wall
textures, flats and sprites into assets.RGBA bitmaps — already
palette-resolved, 4 B/pixel — decoding lazily and caching by name. The
caches are guarded by an RWMutex: render/worldgeo's Builder resolves every
seg's textures while building the static geometry, and the hardware
renderer's texture sync reads them back, so a cache hit (the overwhelming
common case, after the first frame) takes only a read lock and many
callers can resolve concurrently; a genuine miss takes the write lock to
decode and insert.

  WallTexture(name)  composite TEXTURE1/TEXTURE2 texture; falls back to a
                     magenta/black checkerboard for an unresolvable name
                     (visibly wrong, not invisibly missing). Checks the
                     hi-res override set (section 11) first.
  Flat(name)         a floor/ceiling flat, same placeholder policy and
                     hi-res preference.
  Sprite(name)       any single picture-format lump (status-bar digits,
                     faces, keys, viewmodels, world sprites); a
                     missing/malformed name returns ok=false, since HUD
                     code probes for lumps only some IWADs ship. Prefers,
                     in order: an HD weapon-pack frame (section 11), a
                     generated hi-res sprite override, then the WAD's own.

RGBA.TexelsPerUnit records how many pixels of Pix map to one map unit — 1
for anything decoded straight from a WAD, more for a hi-res override
(section 11). Wall/flat/sprite sampling multiplies every texture
coordinate by it before indexing Pix, which is what lets an override's
extra resolution show up instead of the pattern appearing rescaled.

assets.LoadSkybox reads assets/skybox/mars_sky.png from disk (not embedded
— section 18) into the same RGBA format (section 10). assets/sprites.go
builds the sprite-frame index (id's R_InitSpriteDefs) the renderer uses to
pick an 8-way rotation.


8. PACKAGE raster — THE 2D OVERLAY
-----------------------------------
raster.Renderer draws the 2D overlay plane every frame — the weapon
viewmodel, status bar, crosshair and debug HUD text — into a straight-alpha
RGBA8 buffer (raster.Overlay()) that render.Renderer.DrawWorld blends on
top of the GPU-rendered world (section 9). It does no 3D-world drawing of
its own and never touches Vulkan.

raster.New(textures, width, height) sizes the overlay plane to the render
resolution (raster.InternalWidth / InternalHeight, 320x200, are the
fallback when a non-positive size is given) and resolves the weapon/HUD
sprites and fonts through the given assets.Textures. raster.Camera (X, Y,
Z in map units, Angle radians CCW from +X, Pitch radians up+/down-,
FOVDeg) is the engine's one canonical camera type, used throughout —
worldgeo.Camera is built from it each frame for the hardware renderer
(section 9), which clamps Pitch to worldgeo.MaxPitch (89 degrees) — a true
3D camera rotation, not a shear, so it can look almost straight up or
down.

BeginOverlayFrame (called once per frame before the overlay draws) clears
only the rows last frame's draws touched (markOverlay tracks the dirty
span) and rolls the dirty rect forward. Every overlay element is authored
in a 320x200 "HUD space" and mapped to render pixels by hudRect — a
uniform scale plus a horizontally-centred, bottom-anchored offset — through
one of two independent transforms:
  - status bar / HUD: hudScale = hudFit * hudUserScale, where hudFit is the
    320x200 -> framebuffer fit (fills the height) and hudUserScale is
    config.json's hudScale (SetHUDScale). Recomputed when either changes.
    Which HUD draws is config hudStyle (engine hudStyle enum, F1 cycles it
    at runtime): "doom" = the full DrawStatusBar; "quake2" = the minimal
    DrawQuakeHUD; "none" = neither. Legacy showStatusBar:false with no
    hudStyle key maps to "none" (config.Load).
  - weapon viewmodel: hudFit * weaponUserScale (weaponScale / weaponOffX /
    weaponOffY, the weaponSpace=true path through blit; SetWeaponScale from
    config weaponScale). Independent of the status bar's hudUserScale, so
    the two are sized by separate knobs — weaponScale defaults to 1 (fills
    the screen height, the original look).
  - debug text: hudScale for the glyph size but pinned to the top-left,
    ignoring the offset (raster/hud.go).

Weapon viewmodel (raster/weapon.go, DrawWeapon): bottom-anchored,
horizontally centered by the sprite's own pixel size (not its embedded
hotspot offset, which encodes a pseudo-3D projection this project doesn't
reproduce); the muzzle-flash overlay is positioned by the two sprites'
offset DELTA, which still gives correct relative alignment. The gun sprite
is dimmed by the player's sector via light.go's pspriteShade (below); the
flash is full bright. DrawWeapon is skipped entirely while the player is
dead (section 14). Sizing is in the HUD's 320x200 space at the weapon
transform above, so an HD-weapon-pack frame (section 11, TexelsPerUnit 2)
has the same logical footprint as the 1x original and drops in with no
layout change — it just carries more pixels for the GPU upscale.

Weapon bob (engine/weapons.go — g.weaponBob() returns all three per frame,
passed into DrawWeapon). One shared free-running angle WeaponState.bobPhase
advances at dt * bobCycleHz (0.7) * 2pi * g.moveSpeedFrac() — 0 standing,
full at moveTopSpeed — so all three motions freeze at rest and widen with
actual speed, and all read as one arc rather than independent wobbles:
  X  weaponBobMaxX (12 px) * frac * sin(phase)      — side to side.
  Y  weaponBobMaxY (5 px)  * frac * |sin(2*phase)|  — rises once per
     footfall, never dips below rest (SUBTRACTED from gunY, so positive is
     up).
  scale  1 + weaponBobDepth (0.06) * frac * cos(2*phase) — a small
     toward/away size swing (closest at the sway's dead centre, farthest at
     each extreme), so the return half of each swing reads as the gun
     coming back toward the camera. raster.blit takes a `scale` param for
     this; DrawWeapon scales the footprint before centering so it stays
     anchored. weaponBottomOverlap (20 px) hangs the resting gun just past
     the screen's bottom edge (clipped by blit's off-screen check) so a
     sprite that doesn't fill its own bottom rows, plus the Y lift, can't
     crack a gap open underneath.

Sector/distance shading (raster/light.go) is a direct port of PrBoom's
r_main.c R_InitLightTables plus the render-time lookups in r_segs.c /
r_plane.c, baked at init into [16][48] and [16][128] uint16 arrays of
0..256 brightness multipliers — collapsing each of vanilla's 32 COLORMAP
rows to a plain multiply, (NUMCOLORMAPS - row)/NUMCOLORMAPS, since there is
no palette to remap. This is not a leftover from the removed CPU
rasterizer: pspriteShade (the bright, "point-blank" end of a sector's
table — spritelights[MAXLIGHTSCALE-1], so the held weapon has no distance
falloff of its own) shades the weapon overlay above, and BuildLightLUT /
LightScaleValue / AmbientLightValue / LightScaleRef feed the hardware
shader's own uniforms (world.frag's fade(), section 9) so the two shade
identically — a light.go doc comment and light_test.go pin the two against
each other. SetLightScale / SetAmbientLight apply config lightScale /
ambientLight (section 17); ExtraLight is id's "extralight" lever, bumped by
the Heretic Torch/Tome artifacts (section 24) and read back by the hardware
shader too.

Status bar (raster/statusbar.go, DrawStatusBar): takes a raster.HUDStats (a
flat draw-only snapshot the engine rebuilds from PlayerStats every frame —
PlayerStats.toHUD) and draws the real STBAR / STTNUM / STYSNUM / STGNUM /
STFST / STARMS / STKEYS graphics at the exact pixel positions id's
st_stuff.c ST_* constants specify, in 320x200 space (then hudScale'd up).
Health, armour and the ready-ammo number are right-aligned so their
rightmost digit ends at ST_HEALTHX / ST_ARMORX / ST_AMMOX with the '%'
just after (drawPercentField). The four small current/max ammo counters
line up with the STBAR labels BULL / SHEL / RCKT / CELL top to bottom. The
arms widget lights slot 3 for either the shotgun or the super shotgun; the
face shows a health-tier variant, the god face while invulnerable, and
STFDEAD0 once health hits 0.

Quake II HUD (raster/quakehud.go, DrawQuakeHUD): the same HUDStats and the
same graphic lumps, corner-anchored with no status-bar chrome — a big red
STTNUM health number bottom-left beside the MEDIA0 medikit icon, the
ready-ammo number bottom-right beside its pickup sprite (CLIP/SHEL/CELL/
ROCK by ammo type), a small yellow armour count above health with the
ARM1A0/ARM2A0 icon when armour > 0, and the held keys (STKEYS) stacked
top-right. Layout constants (qh*) are in the same 320x200 authoring space
so it obeys hudScale identically.

Debug HUD (raster/hud.go, DrawHUD): a small bitmap-font (Go's basicfont,
7x13/glyph) overlay for level name / FPS / position / angle — toggled by
engine.Game.ShowHUD (on by default; config showDebugInfo).


9. RENDER / RENDER-VULKAN — GPU PRESENTATION
-------------------------------------------
render.Renderer is a two-method interface — DrawWorld, Destroy. The engine
core depends only on this, never on Vulkan directly. Destroy blocks on
device-idle before releasing anything, so callers can invoke it directly
on shutdown.

DrawWorld is the hardware (GPU-geometry) path — the only path the game
uses, stood up by vulkan.NewWorld. render/worldgeo builds the whole level's walls + flats once (wall
quads + BSP-reconstructed subsector-polygon flats, UVs/pegging/fake-contrast
matched to raster) into a static triangle list the backend keeps in a
device-local buffer, rebuilt only when a door/lift moves a sector height
(Builder.Invalidate, engine worldGeomChanged) OR while one is mid-travel:
the sim moves sector heights once per 35Hz tic, so renderFrame lerps them.
runTic snapshots every sector's floor/ceiling into g.prevSectorH before
tickSpecials; renderFrame's hardware branch (applySectorInterp) then writes
prev + (cur-prev)*renderLerp() into g.Level.Sectors for that frame's
geometry build and restores the authoritative values right after — so a
door/lift glides at display rate instead of stepping at 35Hz. A per-tic
change bigger than 48 units is taken to be an instant snap and not lerped.
Presentation only; the sim always reads the real heights. A mid-glide frame
only actually Invalidate()s (which walks every subsector and blocks on a
full static-vertex-buffer re-upload) when the interpolated height rounds to
a DIFFERENT int16 than last frame — renderedSectorHeightsChanged (interp.go)
gates it, since most mid-glide frames land on the same rounded height and
were forcing a needless rebuild + GPU stall every frame. Per frame the CPU
only appends the sprite/voxel-billboard quads. render/worldgeo.ViewProj (byte-matched to
raster's projection) is pushed as a mat4. Each frame the world pass runs a
depth pre-pass over the opaque static geometry (positions only, no colour)
so the colour pass's early-Z rejects occluded wall/flat pixels before the
fade + dynamic light loop, then shades walls/flats/sky, the alpha-tested
2-sided middles, the sprite billboards and the voxel models.

Static-geometry visibility culling (render/worldgeo/visgrid.go, mirroring
engine/collisiongrid.go). Builder buckets its static draws by (texture,
512-unit cell) instead of texture alone — a subsector is bucketed atomically
by its centroid (cellOf), so a cell is only a batching key, never the cull
test. Invalidate records each Draw's REAL vertex bounding box
(Draw.MinX/MinY/MaxX/MaxY); Builder.UpdateVisibility runs a per-frame
camera-vs-box test each frame (camera-inside, or the box's bounding-circle
angular span overlaps the FOV cone + a 15-degree margin — an angular-span
test, not a 4-corner one, so a big box crossing a narrow cone edge-on isn't
wrongly dropped) and fills Geometry.StaticDrawVisible. world.go's colour
pass skips a non-visible Draw and, since per-(texture,cell) runs share a
texture back-to-back more often, caches the last-bound texture + resolved
worldTex to skip the descriptor rebind and texCache lookup. The depth
pre-pass is deliberately left unculled (it draws one contiguous vertex
range, not per-Draw). Testing against the grid cell's nominal square rather
than the draw's real box once black-holed wide outdoor subsectors near
their far edge (fixed in 7c09f19, TestUpdateVisibilityUsesDrawBoundsNot
NominalCell).

world.vert/world.frag: one draw call per texture (a bound set-0 per Draw,
plain Vulkan 1.0 — no bindless), wall/flat/sprite images uploaded once as
device-local mip chains (GPU blit chain) sampled with an anisotropic REPEAT
sampler, a continuous take on vanilla's scalelight/zlight fade computed
directly in the shader (fade() — sector light -> lightnum -> startmap minus
a smooth 1/distance term). Set-0 binding 1 is the run's
brightmap mask (worldgeo.Draw.Bright, resolved once per texture like Tex; a
1x1 black dummy when it has none); world.frag lights a masked texel to
max(sectorFade, luma(uBright)) + a small bloom kicker so a lit panel /
light / EXIT sign stays lit regardless of sector light. Two separate
ambient terms keep a shadowed pixel legible. First, a brightness FLOOR
(config ambientLight, W.light.w — default 0.2, section 17): litAmt is
raised to at least ambientLight * sectorAmbientFrac(), i.e. scaled by how
bright THIS sector is authored, undiminished by camera distance — so a
monster across a lit room stays detailed instead of fading to near-black
by mid-room, while one in a genuinely dark sector gets almost no lift and
needs a real light. 0 reproduces vanilla's crush-to-black in every sector.
Second, on top of that, a faint hemisphere AMBIENT tint (scaled by 1-lit)
keeps a fully-shadowed pixel from crushing to pure black: world.frag's
hemisphereAmbient() mixes a sky-tinted colour (up-facing = floors) with a
darker hue-kept version (down-facing = ceilings) by vNormal.z, all times a
strength scalar. The tint (W.amb.rgb)
is THIS level's
sky bitmap averaged, hue-boosted and scaled ~0.09, computed once and cached
by pointer in worldResources (hemisphereAmbient in world.go) — so a shadowed
corner in a hell map goes murky-warm and one under an open sky goes cool
blue with no per-map tuning. W.amb.w <= 0 falls back to the old flat
vec3(.020,.028,.045). A fully enclosed level (no sky) gets a fixed cool
neutral. voxel.frag applies the same model. Live things
and in-flight projectiles are camera-facing billboards
(worldgeo.Builder.AddSprites, KindSprite / KindSpriteFull for the emissive
projectile path) appended as extra Draws, sized/seated from the sprite
frame's own pixel dims and offsets (section 8's ThingSprite), sorted by
the GPU depth test. This frame's dynamic point lights (muzzle flash, rocket / plasma / BFG
glow, animated map emitters — g.collectLights, section 14) ride in the World UBO as nLights + lightPos[64] /
lightColor[64] vec4 arrays, after a 6-vec4 header (cam, screen, light,
nLights, fog, amb — worldUBOHead = 24 floats), and a trailing
shadowCaster[24] vec4 array (xyz = a grounded thing's floor position, w =
blob radius; w <= 0 ends the list). world.frag's groundShadow() stamps a
soft round dark blob on each up-facing floor pixel under a caster, faded by
distance and by how far the pixel's floor sits from the caster's own (no
bleed onto a step) — always on, no config gate.
engine.collectGroundShadows fills the list nearest-first from the same
grounded-thing filter, capped at hwGroundShadowCap = 24.
The fog vec4 (rgb + density, from config fogColor/fogDensity via
worldgeo.Camera) drives every non-sky exit's fog blend: the vanilla
1 - exp(-density*vDepth) distance term times a HEIGHT term (exp of how far
the fragment / view-ray midpoint sits above a plane ~48u below the eye,
FOG_HEIGHT_AMT = 0.7 mixed) so the fog reads as a low mist pooling in pits
and thinning as you climb. The amb vec4 is the hemisphere ambient tint +
strength above. voxel.frag declares the same 6-vec4 header (even the fields
it ignores) so its lightPos[]/lightColor[] land at the same std140 offset —
a stale voxel header had been reading one vec4 short since fog was added.
The camera world position rides in the spare header slots (cam.w = camX,
nLights.zw = camY,camZ — CAM_POS in the shader) for the water reflection,
fog height and contact-shadow reconstruction.

The head-mounted flashlight (config flashlight, section 14) is a spot term
the point-light arrays can't carry — a beam needs a direction and a cone.
The World UBO gains a Spot* block (pos + 1/radius^2, unit direction,
cos(outer), rgb + intensity, cos(inner); SpotIntensity <= 0 = off) filled
from worldgeo.Camera's Spot* fields, which engine.Game.flashlightSpot
recomputes per frame off the live camera with a handheld sway and a battery
flicker. world.frag adds it as a real Lambert + smooth cone falloff on top
of the sector fade, using the same per-pixel bumpedNormal() the point
lights do.

Cartoon shading (config cartoonShading, hardware only) rides in a repurposed
UBO pad float (CartoonBands, alongside the Spot block): when > 0, world.frag
/ voxel.frag's fade() posterizes its 0..1 brightness to the nearest 1/N
(cartoonLightBands = 4) instead of the smooth gradient. The matching
outline is a worldblit.frag post-chain stage — p4.w carries cartoonOutline
Strength (0.85), and the stage darkens toward black where the world-pass
depth buffer jumps sharply between neighbouring pixels (a silhouette, a
corner, geometry against the sky). Both constants live in render/vulkan/
world.go, deliberately not player knobs.

A floor whose flat is a liquid gets its own vert kind (worldgeo.liquidKind
OfFlat: KindLiquidWater / KindLiquidLava / KindLiquidNukage) and world.frag
shades it — water: the FWATER
texel (sector light only, fade()) is the translucent "bottom", its sample
REFRACTED by the wave slope so it shimmers, then exponentially absorbed
with a depth cue (view angle + view distance: depth = 0.14 + 0.55*graz +
0.34*clamp(vDepth/620) — a wide lake reads deeper toward its far side; red
fastest / blue slowest) so it fades to dark blue-green, plus a waterWave
caustic; then a ripple-displaced desaturated skyColorAt() mixed in by a
SHARP fresnel (0.02 + 0.18*graz^5); a dynamic light shows only as a DAMPED
crest glint; every dynamic light also STREAKS across the surface as a
tight pow(align,48) coloured highlight (reflect the view ray about +Z,
ripple by the wave slope — a cheap SSR stand-in that catches torches /
lava glow / muzzle flash); plus a SUN GLINT — one Gaussian spot near the
horizon whose column drifts with time+yaw, shattered into glitter by
crest^5. waterWave over vWorldPos.xy at W.nLights.y, the seconds clock from
worldgeo.Camera.Time = g.renderClock.
True geometry SSR (hardware): world.frag writes scene ALPHA 0 for water (1
for everything else). rpScene's D32 depth attachment is kept (StoreOp Store,
finalLayout ShaderReadOnlyOptimal) and sampled in worldblit.frag through a
NEAREST depthSampler (dslBlit binding 3). For each alpha-0 pixel the blit
reconstructs the world point from (fragUV*res, linDepth of the sampled
ndcZ) — the exact inverse of raster's column-ray + horizonY/focal mapping,
i.e. worldgeo.ViewProj — reflects the eye ray about the waterWave-rippled
normal, and marches the depth buffer (28 steps, t = 1.32t + 7) for the first
geometry the ray passes behind; that hit's uScene colour is blended in
Fresnel-weighted (0.03 + 0.32*(1-|V.z|)^5) * edge-fade * ssrStrength (0.9).
Rays leaving frame / hitting nothing keep the baked sky reflection. The blit
push constant carries the camera basis for this (p0 exposure,bloomStrength,
waterClock,near; p1 sinA,cosA,focal,far; p2 camX,camY,camZ,horizonY; p3 w,h,
ssrStrength,godrayStrength; worldgeo.NearPlane/FarPlane exported for the
linearise). SSR runs pre-tonemap and does NOT feed bloom (bloom is the
pre-SSR scene).
Lava: warm additive glow past 1.0 (blooms) with the slow sin pulse, and the
dynamic-light term cut to 0.35 (lava is already self-lit). Nukage: a milder
green additive tint. Every worldgeo.Vert carries a unit surface
normal (walls face into their sector, floors up, ceilings down, billboards
at the camera), so world.frag's dynamicDiffuse(N, specMask) is a real
Lambert + Blinn-Phong term: per light, colour*intensity * (1-(d/R)^2)^2 *
(0.35 + 0.65*max(N.L,0) + pow(max(N.H,0),40)*0.6*specMask), summed and ADDED
to the sector fade before the texel multiply. For walls and flats (when
any dynamic light is live) N is not the flat vertex normal but a per-pixel
BUMPED one: bumpedNormal() reads the diffuse texture's own luminance as a
tiny heightfield and perturbs the normal via a screen-derivative cotangent
frame (Schuler — no per-vertex tangents), so a torch or muzzle flash rakes
across brick / panel / grille relief and throws a moving glint instead of a
flat wash. Only the dynamic-light term sees the bump; the baked sector fade
stays flat (it is painted-in art). specMask scales the glint by the texel's
own brightness so metal / lit texels read shinier than matte ones; sprites
and masked mid-textures keep their real normal and a faint fixed specMask;
liquids pass a flat normal and specMask 0 (they have their own glint
models). The world pass renders to an
RGBA16F HDR scene image (values pile past 1.0), and worldbloom.go turns its
bright part into a wide, soft glow with a true MIP PYRAMID:
worldbright.frag Karis-weighted 4-tap downsample + threshold scene -> mip 0
(half res; the 1/(1+luma) weight stops a lone hot texel sparkling), then
worldbloomdown.frag (13-tap Call of Duty ACM) downsamples the chain
mip0->1->2->3->4 (each half the last, ~1/32 res at the bottom), then
worldbloomup.frag (3x3 tent) upsamples back up 4->3->2->1->0 blended ONE:ONE
so each level's blur ACCUMULATES onto the one above. bloomMips = 5 images +
two render passes (rpClear = LoadOp CLEAR for bright/downsample; rpAdd =
LoadOp LOAD + additive pipeline for the upsample). Symmetric SubpassExternal
deps serialise the 9 passes' read-after-write / write-after-read on the
shared mip images (which, like the old ping-pong bloom, are reused across
frames-in-flight). The finished bloom is in mip 0, which the present blit
samples. SetHDR bloom strength 0.85.

worldambient.frag (worldambient.go — renamed from worldshadow.frag/.go when
it grew past dynamic-light shadows alone). One QUARTER-resolution pass
(wr.w/4 x wr.h/4, one shared image reused every frame like worldbloom.go's
mips) that pre-computes three inherently low-frequency terms into an RGBA
buffer — r = dynamic-light shadow (1 = unshadowed), g = SSAO (1 = no
occlusion), b = god-ray glow luma — which worldblit.frag then samples once
at full res through a plain linear sampler. Running SSAO's 12-tap disc
gather and the 24-step god-ray march at 1/16 the pixel count is the real
win; the bilinear upscale from quarter-res IS the soft blur on all three
(no math in worldblit for it). It binds a PREFIX of the real World UBO,
declaring the flashlight Spot* vec4s explicitly even though it only reads
lightPos[] — std140 has no "skip", and the pre-move copy in worldblit.frag
had silently been reading the spot fields as dynamic lights 0..3 (a latent
field-offset bug carried forward fixed).
  - Shadows (dynShadowStrength 0.6, March 320 u, Bias 2 u): for the first
    shadowCasterCount lights (the leading dynamic emitters + up to two
    nearest torches) march uDepth from the pixel toward the light; on-screen
    geometry between them dims that light's falloff-weighted share. Screen-
    space only — an off-screen occluder casts nothing; the shadow-map-atlas
    upgrade is still open.
  - SSAO (ambAOStrength 0.40, Radius 48 u, Bias 1.5 u): reconstruct
    position + a depth-discontinuity-aware normal from uDepth, gather a
    12-sample disc rotated by interleaved gradient noise sampled at this
    pass's OWN quarter-res gl_FragCoord (sampling it at full-res UV strode
    IGN by 4 and aliased into a coarse pattern — a fix chased from a
    grey-speckle report). Then worldambientblur.frag, a 3x3 box denoise on
    the AO channel only (shadow/god-ray pass through — already soft), writes
    the buffer worldblit actually samples: a real blur is what production
    SSAO uses, no dither pattern substitutes for it.
  - God rays (ambGodrayStrength 0.35; ambSunX/Y/Z a fixed ~60-degree world
    sun): project the sun to a screen point, radial-march 24 taps of uScene
    toward it gathering sky (alpha ~0.5) + HDR luma with exponential decay.
    The march's start phase is jittered per pixel (same hash as the AO disc)
    and the contribution is capped — an un-jittered march banded along lines
    toward the sun and could spike the tonemap to flat white on a fast turn.

worldblit.frag then runs the present + post chain in one fullscreen pass,
sampling uScene, uBloom, uOverlay, the world-pass depth uDepth (set 0) and
uAmbientTerm (set 1 — its own dedicated descriptor pool, never touching
worldsetup.go's shared framePool). world.frag writes a material tag in the
scene alpha: 0 = water, 0.5 = sky, 1 = everything else. Order:
  1. water SSR (section above) for alpha-0 pixels.
  2. ambient — one bilinear sample of uAmbientTerm; hdr *= AO (g), then
     hdr += godray(b) * p3.w * a fixed warm tint, then hdr *= shadow (r),
     so a shadowed pixel also dims its own god-ray share (order kept from
     when these ran inline). AO + shadow are world-pixels-only.
  3. Tonemap — ACES filmic (Narkowicz fit) of (scene+bloom)*exposure. The
     old softKnee is kept as a one-line fallback. Output is display-linear;
     the *_SRGB swapchain applies the OETF.
  4. FXAA — console-variant edge AA on the tonemapped image, primary blend
     only (the secondary rgbB min/max-reject refinement was dropped —
     measurable cost, marginal gain). Skipped on water/sky.
  5. CAS — FidelityFX RCAS-shape contrast-adaptive sharpen (p4.x).
     Skipped on water/sky.
  6. Cartoon outline (config cartoonShading, p4.w) — darkens toward black
     where uDepth jumps sharply against its 4 neighbours; runs on
     everything, sky included (a roofline against sky is exactly the
     silhouette a cel look wants). See "Cartoon shading" above.
  7. Screen tint — a full-frame colour wash while the player stands in a
     damaging liquid (engine.hwLiquidTint: lava orange + a slow heat
     wobble, nukage green, blood red), after tonemap, before the HUD so the
     overlay stays true-colour.
  8. Composite the crisp LDR overlay, then a +/-1 LSB triangular-PDF dither
     to kill 8-bit gradient/fog banding.
The blit push constant is 6 vec4 (96 B): p0..p2 the camera basis (SSR
reconstruction), p3 (w, h, ssrStrength, godrayStrength), p4 (sharpen,
dither, ·, cartoonOutlineStrength), p5 the screen tint. The now-vestigial
p6 (dyn-shadow params) and the aoStrength / sunDir / aoRadius fields went
with those effects into worldambient.frag; worldblit no longer binds the
world UBO at all. Tuning consts live in worldambient.go +
recordWorldCommandBuffer; ShadowCasterN + tint come from worldgeo.Camera
each frame. So a coloured torch tints and glows with a moving glint over
the wall relief, a muzzle flash blooms and casts shadows, corners sink into
soft shade, things sit in contact-shadow blobs, a doorway onto the sky
throws light shafts, and wading into lava washes the screen orange.
Per frame: world.vert/frag render into a per-in-flight-slot offscreen
RGBA16F HDR colour image (+ a D32 depth buffer, now StoreOp-Store so the
blit can sample it for water SSR) at render resolution, then worldblit.frag
upscales it letterboxed to the swapchain and blends the un-composited 2D
overlay (raster.Renderer.Overlay — weapon / HUD / crosshair, still
CPU-drawn; raster.BeginOverlayFrame runs only the overlay-plane lifecycle,
section 8) on top. The sky is computed entirely in world.frag
(skyColorAt, section 10): skyPixPerTurn columns per yaw; the vanilla
skytexturemid vertical anchored to the pitch-shifted horizon — pitchShear
rides in the World UBO. Voxel models (cfg.Voxels): worldgeo.BuildVoxelMesh turns a KVX
model into a static vertex-coloured cube-face mesh (cached per model as a
device-local VBO), drawn by a dedicated voxel.vert/frag pipeline inside the
world pass, depth-sorted, per-instance transform+shading in a push
constant; a thing without a model in the pack stays a billboard. Ground
shadows aren't in this path yet. renderer.WarmVoxels meshes the whole pack
up front so no first-sight stall hits the loop — BuildVoxelMesh is a pure
per-model function, so the CPU meshing runs on a GOMAXPROCS worker pool
(buffer creation + the one staging upload stay on the caller); on an E1M2
load with voxels that cut the mesh step ~5.7s -> 1.9s. cmd/isoengine's iso
path instead meshes lazily on first sight (section 23).
bsp.SubsectorPolygons (the flat outlines) clips a map box by every ancestor
partition + seg front line, then hulls with the exact seg endpoints —
236/237 E1M1 subsectors get a flat. A failed NewWorld (no Vulkan driver, or
the device can't stand the pipeline up) is fatal — there is no CPU
fallback (cmd/engine reports the error and exits).

render/vulkan.Renderer is one type that can be built for one of three
mutually exclusive roles, checked at the top of every Draw* method (calling
the wrong one for how it was built returns an error):
  - vulkan.NewWorld / DrawWorld — the hardware (GPU-geometry) path above.
    The game's only renderer.
  - vulkan.NewIso / DrawIso — the isometric top-down path (section 23).
  - vulkan.New / DrawFrame — upload a whole CPU-drawn RGBA8 frame into a
    GPU texture and blit it with one fullscreen triangle, nothing else.
    Used directly (not through the render.Renderer interface) by the
    pre-game launcher and the level editor to present their own 2D GUIs
    (both drawn on the CPU via package imkit — sections 22, 25),
    unrelated to how the game itself renders a level. The vanilla-shaded
    CPU-rendered-world present path this once also served no longer
    exists.

Setup (vulkan.New / NewWorld / NewIso all share this): create instance (+
the KHRONOS validation layer only if present AND debug was requested —
cmd/engine requests it only under TPF_VK_DEBUG; + VK_KHR_
portability_enumeration and the matching create flag only where the loader
advertises them, so MoltenVK on macOS exposes its device — inert on native
Windows/Linux drivers, see section 21) -> GLFW window surface -> pick the
best physical device (prefers a discrete GPU; logs DeviceName /
DeviceTypeName / DeviceIsSoftware so a CPU/software Vulkan fallback is
visibly flagged) -> logical device (+ VK_KHR_portability_subset when the
device advertises it, spec-required) + graphics/present queues ->
swapchain -> image views -> render pass -> framebuffers -> command
pool/buffers -> sync objects. NewWorld/NewIso then build their own
additional pipelines/resources on top (world.go / isosetup.go); plain New
instead builds the frame-upload texture (R8G8B8A8_UNORM, linear sampler) +
one mapped staging buffer per frame-in-flight slot -> descriptor set -> the
blit pipeline.

Per frame (DrawFrame, the plain CPU-buffer path): a minimized window (0x0
framebuffer) skips the frame; a swapchain flagged out of date is rebuilt
first (recreateSwapchain). Then: wait this slot's in-flight fence, memcpy
the CPU frame into this slot's mapped staging buffer, acquire a swapchain
image, wait the fence of whichever earlier in-flight frame last used that
image (imagesInFlight) before reusing its command buffer, record a command
buffer that transitions the frame texture, copies this slot's staging
buffer into it, transitions it shader-readable, then runs the render pass
— bind the trivial blit pipeline (one hardcoded fullscreen triangle from
gl_VertexIndex, no vertex buffers), set the dynamic viewport/scissor via
letterboxViewport (the largest centered rectangle preserving the source
frame's exact aspect, black-boxing rather than stretching), bind the
descriptor set, draw 3 vertices — submit and present. A
VK_ERROR_OUT_OF_DATE_KHR / VK_SUBOPTIMAL_KHR from acquire or present sets
a "recreate next frame" flag instead of returning an error, so a window
resize doesn't terminate the loop. DrawWorld/DrawIso follow the same
acquire/submit/present bookkeeping, recording their own richer command
buffers instead of the trivial blit.

maxFramesInFlight is 2, so the CPU can build and upload frame N+1 while the
GPU is still finishing N. What makes that safe (plain DrawFrame): one
host-visible staging buffer per slot (a memcpy for the next frame can't
land on a buffer the GPU is still reading — DrawFrame waited that slot's
fence); the single frame texture guarded by a record-time barrier whose
source scope is the previous blit's fragment-shader sampling; and
imagesInFlight[i] tracking which slot's fence last covered swapchain image
i, waited on before that image's command buffer is re-recorded.
renderFinished semaphores are sized per swapchain image (not per in-flight
slot), since a binary semaphore can't be re-signaled until the
presentation engine is entirely done with it. recreateSwapchain (on
resize/monitor change) waits for device idle, then rebuilds the swapchain
and everything sized to it — reusing the render pass and pipeline. The
frame-upload texture is fixed at the configured render resolution and
untouched by a resize; the blit rescales it.

Shaders (render/vulkan/shaders/*.vert, *.frag) are precompiled to SPIR-V
and embedded via go:embed; nothing compiles at runtime. Recompile after an
edit and commit the regenerated .spv:
  - Windows: render/vulkan/shaders/compile.ps1 (glslc, from the Vulkan SDK).
  - Linux/macOS: render/vulkan/shaders/compile.sh — prefers glslc, falls
    back to glslangValidator on PATH, then to a copy under <repo>/.tooling/
    (gitignored; download the KhronosGroup/glslang release tarball's
    bin/glslangValidator there). glslangValidator output is unoptimized —
    a few KB larger, functionally identical. Pass base names to compile
    just those: `compile.sh world.frag`.


10. THE SKYBOX
--------------
The sky is not positioned in the 3D world — there is no "sky sector" out
past a level's walls. world.frag's skyColorAt (section 9) computes it
per-pixel from the camera's view direction whenever a wall/flat vertex is
tagged with the sky material key, instead of sampling a texture through
the normal UV path.

Texture source: the WAD's own sky texture for the current map, PICKED THE
WAY PrBoom DOES (skyTextureForMap, p_setup.c's P_SetupLevel): SKY1..4 by
episode for Doom / Ultimate Doom, and SKY1 (MAP01-11) / SKY2 (12-20) / SKY3
(21+) for Doom II & Final Doom. These are TEXTURE1 entry names (the Doom II
ones wrap the RSKYn patches), so they resolve through WallTexture for
either game; a missing one falls back to SKY1. render/worldgeo.Builder
resolves it once at level load (New) and again on a UMAPINFO `skytexture`
override or a map change (SetSkyName, engine.Game.ApplyMapInfo).

Mapping (skyColorAt, mirroring the removed CPU rasterizer's own):
  - Horizontal (u): the per-pixel view angle (from the pixel's screen
    column, the same as every other column's projection) plus a
    whole-texture offset for the camera's yaw. A narrow WAD sky scrolls at
    id's ANGLETOSKYSHIFT rate — skyPixPerTurn = 1024 texture columns per
    360-degree turn, so a 256-wide sky wraps 4x (the vanilla feel).
  - Vertical (v): anchored to the vanilla skytexturemid convention (id's
    "100*FRACUNIT", not the texture's geometric centre) at the
    pitch-adjusted horizon row. The per-row texel rate is scaled by 200 /
    render height (raster's own reference height), so the sky fills the
    same share of the view at any resolution instead of tiling as it rises.
    Looking up/down shifts which slice is visible.
  - Walking never moves the sky (not a function of camera X/Y).

Known gap: the external Mars panorama (a 4096x2048 daytime sky generated by
tools/gensky, loaded from disk via assets.LoadSkybox — not embedded,
section 18; colour follows NASA's description of Mars, rusty orange-brown
paling toward the horizon with a pale-blue forward-scatter halo near the
sun) that used to override every level's sky regardless of WAD is currently
NOT wired into the hardware renderer — assets.LoadSkybox and
worldgeo.Builder.SetSky (which would install it) both still exist, but
nothing calls SetSky any more. It regressed silently when the CPU software
rasterizer (which owned this priority) was removed; every level currently
shows its own WAD sky texture instead of the panorama regardless of whether
assets/skybox/mars_sky.png is present. Re-wiring it (cmd/engine calling
SetSky after loading it) is a small, self-contained follow-up.


11. HI-RES TEXTURES & HD WEAPONS
--------------------------------
Every wall texture and flat DOOM1.WAD itself defines (125 wall textures, 53
flats — everything but F_SKY1) has a procedurally upscaled, more-detailed
replacement, preferred over the WAD's own composed texture whenever a level
references one of these exact names (assets/hires.go). A different WAD/PWAD
referencing other names falls straight through to that WAD's data — the
override set is a preference, not a requirement.

No third-party HD pack is bundled — a community pack (DHTP and the like) is
a derivative of id's copyrighted art, often hundreds of MB, with its own
redistribution terms, the same "supply your own locally" story as the WADs.
Instead tools/gentex decodes each texture/flat at its real WAD-authored
pixels (the same wad.ComposeTexture / wad.DecodeFlat path the renderer
uses) and runs it through enhance():
  1. Bilinear upscale by assets.HiresTexelsPerUnit (4x per axis, 16x area).
  2. A box-blurred copy of that upscale feeds a Sobel edge detector —
     blurring first matters: edge detection on the raw upscale finds
     "edges" everywhere and re-emphasizes the blockiness. Only edges that
     survive the blur (a panel seam, a mortar line) get a thresholded,
     proportional darkening — a cheap ambient-occlusion-like bevel.
  3. Smooth low-frequency value noise (a coarse random grid, bilinearly
     interpolated) is added as gentle brightness mottling — material grain,
     not sensor noise.

Output PNGs live in assets/textures/walls/, .../flats/ and .../sprites/,
loaded from disk into a name -> *RGBA map at startup, independent of the
WAD. Those three directories are also where a real hi-res pack goes:
indexHiresDir walks them recursively, keyed by the upper-cased file stem,
and a level then prefers assets/textures/walls/STARTAN3.png over the WAD's
composed STARTAN3. Because lookups are by lump name, one populated
directory serves DOOM1.WAD and Doom2.wad at once. A pack's images aren't
all a fixed 4x, so loadHiresOverride derives each file's RGBA.TexelsPerUnit
from pngWidth / originalWidth (the TEXTURE1 width for a wall, 64 for a
flat, the patch width for a sprite), clamped to [0.5, 16]. Nothing about a
pack is committed — .gitignore excludes /assets/textures/ and
/assets/skybox/.

Quake 1 texture pack (config's quake1Textures, off by default). A Quake map
uses none of Doom's texture names, so a Quake pack can't just be dropped in
the way a DHTP-style Doom pack can — the two games' art has to be paired up
by hand. tools/importquake does that conversion offline: it reads a curated
Doom-lump -> Quake-file table (tools/importquake/mapping.txt, ~426 rows over
the full vanilla DOOM1 + Doom II wall + flat set), pulls each named .tga
out of the pack (assets/import/Quake1_Textures.pk3), decodes it (a small
24/32-bit, raw-or-RLE Targa reader — tools/importquake/tga.go), optionally
caps the long edge (default 1024, Catmull-Rom), and writes it as
assets/textures/quake1/walls|flats/<DOOM_LUMP>.png. Notably the GATE1..4
teleporter-pad flats map to the pack's swirling teleport-vortex textures
(#RTeleport15 / #teleport0), so a pad's animation cycle reads as a pulsing
sci-fi effect rather than a flat colour swap. That is a fourth override
directory, indexed by indexQuakeWalls/indexQuakeFlats exactly like the
hi-res set. WallTexture/Flat consult it ONLY when SetQuake1Textures(true)
has been called (cmd/engine passes config's quake1Textures), and then it
wins over the assets/textures/walls|flats hi-res PNG for any name the table
covers; every other name is untouched, so the pack layers on top of the
existing hi-res set rather than replacing it. The importer never writes into
assets/textures/walls|flats, and .gitignore excludes both /assets/import/
(the raw pack) and /assets/textures/ (the converted output).

Heretic HD texture pack (assets/textures/heretic/, Heretic sessions only —
section 24). A community Heretic HD/PBR pack ships its base-colour PNGs
already named by Heretic lump name (a Doomsday jHeretic tree), so unlike the
Quake pack it needs no pairing table. tools/importhereticpbr reads the .pk3
and routes Data/jHeretic/Textures/*.png -> assets/textures/heretic/walls/,
Data/jHeretic/Flats/*.png -> .../flats/ (a byte copy; -max downscales via
Catmull-Rom and re-encodes). It ignores the PBR maps (normal / specular /
metallic / roughness / displacement / AO — this renderer has no use for
them), the 32-frame liquid animations (never referenced by name), and
SKY1..3 (section 10's job). Textures.SetHeretic(true) — cmd/engine calls
it when w.IsHeretic() — makes WallTexture/Flat consult hereticWalls/
hereticFlats AHEAD of the Quake pack, the generic hi-res set and the WAD;
the directory is separate precisely because the pack's Doom-name collisions
(SW1OFF, DOORSTON, ...) must not touch a Doom session. loadHiresOverride
derives each file's density from pngWidth/def.Width as usual. Names the pack
doesn't cover fall straight through to heretic.wad's own composed texture.

HD weapon viewmodels (assets/weapons/*.pk3, assets/weapons.go): a separate
override just for the first-person weapon sprites, because the interesting
packs for those ship as a GZDoom .pk3 (hires/sprites/<weapon>/<LUMP>0.png
inside a zip), not a loose PNG tree. loadWeaponPack reads every .pk3 in
assets/weapons/, decodes each PNG eagerly (the set is only a few dozen
frames / a few MB, unlike the lazily-indexed texture set) and keys it by
lump name. Textures.Sprite then prefers a pack frame over BOTH the WAD's
own psprite and any generated hi-res sprite override: density is the exact
PNG/original-patch-width ratio (these packs are a clean 2x) and the hotspot
is the WAD patch's scaled by it. A frame whose weapon the loaded IWAD ships
no sprite for (SSG/plasma/BFG under shareware) still resolves — at
weaponPackTexelsPerUnit (2.0) with a synthesised centred-bottom hotspot,
since DrawWeapon centres the gun by its own pixel size and only the
muzzle-flash offset delta wants the real hotspot. .gitignore excludes
/assets/weapons/.

Making the extra resolution visible needed one renderer change beyond
swapping the image. Wall/flat sampling always worked in Doom's "1 texel =
1 map unit" convention — a coordinate in map units indexed pixels
directly. A 4x image at the same physical wall size breaks that twofold:
naively it would touch a texel every 4 pixels (no detail gain) and wrap 4x
later (the pattern would look 4x larger). Both are fixed by
RGBA.TexelsPerUnit (section 7): every map-unit texture coordinate is
multiplied by it just before the final floor+wrap, so a 1:1 WAD texture is
unaffected while an override samples its full detail at the same apparent
scale. wallPiece anchoring (which adds a texture's height to a
floor/ceiling height for unpegged textures) needs the same correction —
tex.Height is a pixel count, divided back down by TexelsPerUnit to get map
units.


12. PACKAGE window — OS WINDOW & INPUT
-------------------------------------
GLFW-backed (ClientAPI = NoAPI, since Vulkan owns the GPU). window.Window
is the engine's only dependency on GLFW — every other package talks to this
package's small API, so a future non-GLFW backend is a reimplementation of
this one file. window.WADFromCommandLine returns an explicit WAD path —
$TPF_WAD or a *.wad command-line argument — which is what makes the engine
usable headless or from a script and bypasses the launcher entirely
(section 2). window.PickWADFile (picker.go) is the OS's native file-open
dialog, filtered to *.wad — now the "Browse..." button inside the launcher
(section 22) rather than the first thing at startup. pickWAD is the one
build-tagged seam: picker_dialog.go (windows || darwin) uses
github.com/sqweek/dialog (Win32 GetOpenFileName / Cocoa NSOpenPanel);
picker_unix.go (everything else) shells out to
zenity/qarma/matedialog/kdialog, deliberately keeping Linux off a
compile-time GTK dependency. See section 21.
window.NewFixed(w, h, title) is window.New's sibling for the launcher: a
fixed-size (non-fullscreen, non-resizable) window with a GLFW lifecycle
that survives being created and destroyed before the game's own window,
which window.New alone did not. window.MenuKey* / MenuKeyDown / TakeTyped
Raw are the launcher's text-editing and navigation key plumbing (section
22), unused by the game itself.
window.PickMap(maps, def) is the companion for the start-level choice when
there's no console, one build-tagged file per OS: zenity --list /
kdialog --menu on Unix (picker_unix.go; needs $DISPLAY / $WAYLAND_DISPLAY),
PowerShell Out-GridView on Windows (pickmap_windows.go), osascript
"choose from list" on macOS (pickmap_darwin.go). Each returns def on
cancel and ErrPickMapUnavailable when its helper is absent (Server Core, a
headless box). Map names are sanitised to [A-Za-z0-9_] before going into
the shelled-out command. window.StdinInteractive (tty_unix.go TIOCGWINSZ
ioctl / tty_windows.go GetConsoleMode) is how chooseStartMap tells "run in
a shell" from "double-clicked" — a plain character-device test would
wrongly call /dev/null a terminal.

window.New(width, height, title, fullscreen): fullscreen (the default;
config's "windowed" opts out) makes an undecorated, non-resizable window
sized to the primary monitor's current video mode and positioned at its
origin — borderless windowed fullscreen, so alt-tab is instant with no
mode switch. width/height (config windowWidth/windowHeight) are used only
for the windowed case, where they set both the window size and the render
resolution (section 17, Config.RenderSize).

Input is polled, not event-driven: Window exposes one boolean per action
(ForwardPressed, StrafeLeftPressed, TurnLeftPressed, RunPressed,
UsePressed, FirePressed, EscapePressed, WeaponKeyPressed(1-7)) plus
MouseDelta. EnableMouseLook switches GLFW into disabled-cursor mode (an
unbounded virtual position instead of clamping at the screen edge) plus
raw, OS-acceleration-free motion where supported; MouseDelta reports pixel
deltas since the last call for engine/game.go to turn into yaw/pitch. A
real input system with configurable bindings is future work; these queries
are the placeholder scheme.


13. PACKAGE audio — SOUND
------------------------
One output stream for the whole engine, structured like PrBoom's
i_sound.c rather than vanilla Doom's split between a PCM mixer and a
separate MIDI device. The public surface is the same on every OS (Device:
NewDevice / PlaySound / PlaySoundVol; MusicPlayer: NewMusicPlayer / Play /
Stop); only the MIDI synth backend is build-tagged.

The shared software mixer (mixer.go, all platforms) owns the single oto
stream — S16 stereo at 48 kHz — and runs the audio callback:
  - a fixed pool of effect voices (mixVoices = 16), each a fractional read
    cursor into an 8-bit 11 kHz DMX clip with linear interpolation to the
    output rate; oldest-wins stealing when all voices are busy — the shape
    of I_UpdateSound;
  - the music synth's rendered block, when a pull-mode MIDI backend has
    installed its render hook (setMusicRender);
  - master SFX/music gains with headroom, then a hard clip.
  Env knobs, no rebuild: TPF_SFX_GAIN (0.5), TPF_MUSIC_GAIN (0.5),
  TPF_AUDIO_MS (55 — raise if it crackles). One stream for effects and
  music together (rather than oto's plus FluidSynth's own) keeps every
  8-bit 11 kHz clip off the OS resampler and out of a second small buffer
  on a non-RT thread.

audio.Device is a thin handle to that mixer: PlaySound/PlaySoundVol add a
voice. PlaySound plays at the clip's own level; PlaySoundVol takes a
per-sound multiplier that Game.playWeaponSound uses for the weaponVolume
knob and Game.playWorldSound for the worldVolume knob (level machinery —
section 14). Game.playSound looks lumps up through a per-name cache;
soundDuration reads a cached lump's length in seconds.

audio.MusicPlayer streams a decoded MUS event stream to a MIDI synth,
looping indefinitely. The MUS timing loop and the wait-for-the-previous-
goroutine track-switch discipline are shared (musicloop.go, all
platforms); each backend supplies only send/silence/reset.
MusicPlayer.SetVolume(v) (audio.go, all platforms) sets the config
musicVolume knob: it scales mixer.musicVol on top of the TPF_MUSIC_GAIN
master, so it only affects a synth rendered THROUGH the mixer (FluidSynth,
Linux and Windows) — a no-op on the winmm fallback and the stub player.
cmd/engine / cmd/isoengine call it once, with cfg.MusicVolume, when they
start a session's music; the value rides the shared mixer across launcher
trips. FluidSynth is
driven in PULL mode on both Linux and Windows — it opens no audio device
of its own; the mixer calls fluid_synth_write_s16 from its output callback
and sums the block with the effects, the way PrBoom renders its MIDI
player into the SDL callback.
  - Windows (midi_windows.go picks the backend; fluidsynth_windows.go,
    winmm_windows.go): FluidSynth with a bundled soundfont when the DLLs
    and a .sf2 are present — loaded at runtime by cgo LoadLibrary, since
    purego's Windows amd64 path can't pass the double args
    fluid_settings_setnum needs — rendered into the shared mixer. Otherwise
    a clean fall-back to winmm.dll's MIDI_MAPPER (the Microsoft GS
    Wavetable synth), which needs nothing installed and plays on its own
    output (it is the OS synth, not something we can pull). $TPF_SOUNDFONT
    overrides the .sf2 search (exe dir + parents, a soundfonts/ subdir,
    cwd).
  - Linux (midi_linux.go): the same, via libfluidsynth loaded at runtime
    with purego (no cgo, no -dev package). NewMusicPlayer returns an error
    (music simply disabled, engine runs on) when libfluidsynth or a
    soundfont is absent; $TPF_SOUNDFONT overrides the .sf2 search.
  - Others (midi_other.go): no-op stub.
Switching tracks or calling Stop waits for the previous playback goroutine
to exit (a done channel) and then drops the mixer's render hook under the
mixer lock, so the synth is never torn down while the audio thread or a
goroutine might still be using it. The music is driven entirely from
cmd/engine (audio.PlayLevelMusic on load, OnLevelChange / OnMusicChange on a
transition); the engine core holds no music handle. audio.Setup builds the
device + player ONCE per process, outside the launcher<->session loop
(section 2), so a session opened with config music:false silences the
previous session's track with Play(nil) — a documented no-op-events restart
that halts and all-notes-offs the current track without touching the
backend — rather than Stop(), which is a one-way teardown.


14. PACKAGE engine — GAME LOOP & CORE SYSTEMS
--------------------------------------------
Idiomatic Go — interfaces as contracts, composition over inheritance,
polymorphism through interface slices. The per-frame simulation is an
ordered []System driven by Game.Run rather than a hand-written call
sequence:

  engine.System   interface{ Name() string; Update(g *Game, dt float32) }
                  — a self-contained slice of per-frame behavior. Adding a
                  subsystem is a registration in NewGame, not a loop edit.

Registered in NewGame, order load-bearing:
  movementSystem  input, momentum, collision, the vertical fall arc, jump
                  (Space) — settles the camera (handleMovement).
  useSystem       edge-detects E and activates the nearest special
                  line in front of the player — doors, switches, exits.
                  While the player is dead, E instead restarts the
                  current level (restartLevel: fresh-spawn loadout, then a
                  reload queued through pendingWarp like a level exit).
  combatSystem    weapon-slot keys (edge-triggered) and fire (held,
                  auto-refire), then advances the viewmodel animation and
                  in-flight projectiles. While the player is dead it still
                  advances projectiles and the weapon lower, but takes no
                  new fire/switch input.
  cheatSystem     feeds typed keys (window.Window.TakeTyped, a GLFW char
                  callback) into the classic-cheat matcher — iddqd, idkfa /
                  idfa, idclip / idspispopd, idbehold[vsiral], idclevXY,
                  idmusXY, idchoppers, idmypos (cheats.go). A testing aid,
                  always on, no config gate; every hit logs "engine: cheat:".
                  No-op without a window (tests).
  flashlightSystem  toggles the head-mounted flashlight on F (edge-
                  triggered), and resets raster.ExtraLight to 0 each frame
                  so a later system (artifactSystem, for Heretic's Torch/
                  Tome) can still bump it for its own reason (flashlight.go).
                  A no-op when config flashlight is false or there is no
                  window. See "Flashlight" below.
The sector effects those spawn are advanced on the 35 Hz tic, not here.

An alternate front end (cmd/isoengine, section 23) keeps this whole system
list but replaces slots 0 and 1 in place — game.ReplaceMovementSystem(engine
.IsoMovementSystem{}) and game.ReplaceUseSystem(engine.IsoUseSystem{}) — so
thrust is screen-relative to a top-down camera azimuth and "use" is a
proximity search rather than a facing ray, while everything downstream
(combat, cheats, flashlight, the 35 Hz sim) is untouched. That front end
also drives the loop itself (Game.AdvanceSimulation per frame in
game.Run's place), so ordering among the systems still holds.

Flashlight (engine/flashlight.go). F is a persistent on/off toggle (no
battery drain). It is a real forward spot cone — Game.flashlightSpot
builds a flashlightSpotLight each render from the live camera (with a
sub-degree handheld sway and a subtle battery-flicker on flickerWobble),
carried in worldgeo.Camera's Spot* fields and lit by world.frag
(SpotIntensity <= 0 = off). Its radius (1400 u) deliberately outreaches the
muzzle flash so a monster reads as lit and detailed well before
point-blank.

engine.Game owns the Window, the render.Renderer (the hardware/GPU-geometry
backend), the raster.Renderer (the 2D overlay compositor, section 8), the
loaded WAD/Level/BSP tree, the Camera, player movement state
(VelX/VelY/VelZ, PlayerZ, onGround), PlayerStats, WeaponState, the
AudioDevice, every live Mobj, the active sector thinkers and in-flight
projectiles, the optional voxel pack, the map's static light emitters, and
the ordered []System. Run drives the per-frame sequence in section 4; it
clamps dt to maxFrameDelta (0.1 s) first, so a hitch — asset decode,
alt-tab, window drag, a breakpoint — can't spike momentum or jump the
camera far enough to tunnel through geometry.

Movement (handleMovement): WASD relative to facing, Left/Right arrows or
mouse-look to turn, hold either Shift to run, momentum-based translation
ported from id's P_XYMovement / P_Thrust — holding a direction key adds
thrust to velocity every frame rather than setting it, and a
multiplicative friction applies every frame regardless of input:
  moveTopSpeed   = 300 map units/sec — this project's chosen top speed.
                   Turning has no vanilla momentum to port, so it is a
                   direct rate: 2.5 rad/sec keyboard, 0.0022 rad/px mouse.
  frictionPerTic = 59392/65536 (id's ORIG_FRICTION), applied as
                   frictionPerTic^(dt*35) to stay frame-rate independent.
  stopSpeed      = (4096/65536)*35 units/sec (id's STOPSPEED): below this,
                   momentum snaps to zero instead of decaying forever.
  thrustAccel    = back-derived so holding a key settles at exactly
                   moveTopSpeed once thrust and friction balance.
  runMultiplier  = 2.0 — thrust while Shift is held (id's walk vs. run
                   forwardmove is exactly 2x).
Both thrust and friction are gated on (g.onGround || wedged): id's
P_MovePlayer only P_Thrusts while `onground`, and P_XYMovement skips
friction while `mo->z > mo->floorz`. So there is no air control, and you
keep full horizontal speed through a fall — landing much further out if you
ran off the ledge than if you walked. The `wedged` exception (handleMovement
computes it as !canMoveTo at the player's own position) restores thrust +
friction with the feet off the ground when the player is stuck, so a bad
landing can be pushed out of. While the player is dead, handleMovement
zeroes horizontal velocity and only runs resolvePlayerZ.

Jump (Space, edge-triggered in handleMovement): from the ground only, sets
g.VelZ = jumpImpulse (8 units/tic, ZDoom's default player.jumpz, as
units/sec) and clears onGround; resolvePlayerZ's fallStep then runs the arc.
Against playerFallGravity the apex clears a bit over a maxStepUp (24u)
ledge. The ledgeLaunchBoost horizontal kick is suppressed on a deliberate
jump (it only fires when the feet leave the ground already heading down,
nvz <= 0) so a jump keeps its own arc.

Camera.Angle is wrapped to (-2pi, 2pi) every frame. Vertical position is
real: resolvePlayerZ runs id's P_ZMovement each frame (converted to
continuous time like friction). The player has feet height g.PlayerZ and
vertical momentum g.VelZ; walk off a ledge and PlayerZ stays put while the
new sector's floor drops below it, so gravity takes over:
  gravityAccel      = 1 unit/tic^2 = 1225 units/sec^2 — id's GRAVITY.
  playerFallGravity = gravityAccel * fallGravityScale (0.7) — what the
                      player ACTUALLY falls under. A softer fall = longer
                      air time = a run-off clears more ground (~1/sqrt of
                      the scale). A deliberate gameplay choice for
                      gap-jumping between raised platforms.
  ledgeLaunchBoost  = 1.35 — a one-time multiply on horizontal momentum
                      the instant the feet leave a ledge, only above
                      ledgeBoostMinSpeed (100 u/s): a committed run-up
                      jumps much further than a slow step-off.
  fallStartKick     = 2 units/tic (id's `if (momz==0) momz = -GRAVITY*2`).
  hardLandingSpeed  = 8 units/tic — descent past this grunts ("DSOOF") and
                      dips the view (springs back at viewDipRecover).
  terminalFallSpeed = 2500 units/sec — a safety cap for a single big frame.
Landing snaps PlayerZ to the floor and zeroes VelZ; stepping onto ground
<= maxStepUp higher snaps up the same way (no smooth step lerp). The eye
is PlayerZ + EyeHeight (41 map units, id's constant) + the recovering
viewDip, clamped just under a low ceiling.

Collision (engine/collision.go, engine/collisiongrid.go): tryMove
subdivides the frame's move into steps no longer than playerRadius/2 and
clips each (stepMove: full (dx,dy), then X-only, then Y-only — a simple
axis-separated slide along walls) — substepping so a fast frame can't
carry the player across a wall thinner than playerRadius between checks.
canMoveTo(x, y, fromFloor) has a nearby-line scan plus a destination-sector
check:
  1. anyLineWithin(x, y, playerRadius = 16) — a one-sided Linedef within
     radius blocks outright. A two-sided Linedef blocks only when the
     radius-square box at (x,y) actually STRADDLES it (boxStraddlesLine, id's
     P_BoxOnLineSide != -1) AND its opening is shorter than playerHeight =
     56, OR the step up across it (max of the two sector floors - fromFloor)
     exceeds maxStepUp = 24, OR its far-side ceiling is < playerHeight above
     fromFloor. Gating those on "box crosses the line" is load-bearing: a
     body merely near a two-sided line but wholly on one side of it (e.g.
     standing under a ledge you just walked off) must not be constrained by
     it — otherwise every direction freezes; and measuring the step-up
     against the LINE'S opening the moment the box reaches its plane (not
     only against the destination centre point's sector, which the centre
     doesn't enter until ~playerRadius past the wall face) is what stops the
     player visibly walking into / through a tall two-sided step before the
     move is finally refused. "Nearby" is resolved through g.blockGrid, a
     uniform 128-unit-cell spatial grid built once in NewGame over the
     parsed Linedef data (section 18).
  2. a step-up check seeded from the DESTINATION point's own Sector via
     bsp.PointSector: destFloor - fromFloor must be <= maxStepUp = 24
     (a backstop for a destination reached across several lines). There is
     no "too far to drop" rejection — real Doom exempts the player. The
     destination sector's own floor-to-ceiling clearance must also be
     >= playerHeight.
(engine/map.go's pCheckPosition/pTryMove — the monster/mobj path — still
takes every in-radius two-sided line's opening ungated; monsters avoid
dropoffs so they rarely reach the "frozen under a ledge" state, but folding
that path onto the same straddle test is an open follow-up.)

Stuck recovery (stepMove): if canMoveTo already fails at the player's
CURRENT position (a landing wedged in a pocket too tight for the normal
axis slide, a sector risen into them, an awkward teleport) the normal clip
refuses every direction. stepMove then also accepts a sub-step that
strictly increases playerWallClearance — the distance to the nearest
blocking line (lineBlocksPlayer) — so the player can crawl toward open
space instead of freezing. Gated hard to the already-stuck state and to
strictly-looser sub-steps, so it can't be used to squeeze through a wall.
Pairs with handleMovement's `wedged` thrust/friction exception (so a
mid-air wedge still builds the velocity stepMove needs to work with).

Doors (engine/doors.go): the E "use" action raycasts from the camera
along its facing and activates the nearest door-special Linedef within
useRange = 64. Only manual / use-activated door specials are handled here
(1/26-28/117 open-wait-close, 31-34/118 open-and-stay; keycard-locked
variants check PlayerStats.Keys). Each active door is a doorThinker
animating one Sector's ceiling at doorSpeed = 70 units/sec (id's
VDOORSPEED) between its closed height and lowestAdjacentCeiling - 4, with a
~4.29 s pause fully open before an auto-close door closes. The animated
height is written straight into g.Level.Sectors — the same slice the
renderer and collision read — so an opening door is immediately visible
and walkable. A used manual door always moves the sector behind the line —
`sides[line->sidenum[1]].sector`, id's EV_VerticalDoor exactly. Doom's maps
wind a door line so its back sidedef faces the door sector, and a
two-linedef door (openable from both sides — Doom II MAP01's exit, DOOM
E1M1's last door) gives BOTH lines the same back sector, so this is right
from either approach. (An earlier player-side heuristic here opened the
front sector for some windings — e.g. E1M1's last door pushed from the
front of its far linedef — and that door never moved.)

Weapons (engine/weapons.go): nine weapons in id's weapontype_t order —
Fist, Pistol, Shotgun, Chaingun, Rocket Launcher, Plasma Rifle, BFG9000,
Chainsaw, Super Shotgun — on seven keyboard slots: slot 1 toggles
Fist/Chainsaw, slot 3 toggles Shotgun/Super Shotgun, the rest hold one.
Each is a WeaponDef with its fire/flash animation flattened from id's
info.c state chains into plain frame-letter + tic-count slices, a fire
sound, and an ammo type/cost; the chainsaw additionally has an IdleFrames
loop for its SAWG C/D vibration and an IdleSound (DSSAWIDL), re-triggered
every idleSoundInterval (~0.68 s) while it sits ready. WeaponState is a
small phase machine (lowering -> raising -> ready -> firing) driven by
weaponRaiseSpeed (id's RAISESPEED/LOWERSPEED — 16 tics to fully raise or
lower). One deliberate non-vanilla tuning: the Chaingun's fire frames are
2 tics each (4 tics/shot, ~8.75/sec) rather than id's 4 — twice the vanilla
rate, per project preference; its flash is pulled in to 3 tics to match.
FireWeapon is a no-op unless the weapon is ready with enough ammo;
beginFire does the shot, and updateWeapon also calls it at the end of a
held weapon's fire animation to auto-refire seamlessly (id's 0-tic
A_ReFire). A weapon can carry a FireSoundSeq — one-shot sounds at fixed
tic offsets partway through the animation; only the Super Shotgun uses it
(DSDBOPN / DSDBLOAD / DSDBCLS at the C / D / F frames).

FireWeapon dispatches by kind. The four hitscan guns resolve instantly via
pLineAttack. The SSG is id's A_FireShotgun2 verbatim — 2 shells a shot, 20
pellets, each spread twice as wide horizontally as the plain shotgun AND
jittered vertically (~+-7 degrees), over the slowest animation of any
weapon (~54 tics). Doom II MAP01 places no single-player SSG (its two SSG
things are MTF_NOTSINGLE, skipped by spawnMapThings exactly as vanilla);
the first pickable one is on MAP02. The chainsaw does a very short-range
pLineAttack every fire frame for no ammo. The three projectile weapons
spawn a real traveling Projectile. Ownership lives in PlayerStats.Weapons;
pickups grant it and light the status-bar arms widget for slots 2-7.

Projectiles (engine/projectiles.go): a Projectile carries its own copy of
its ProjectileDef (sprite, speed, explosion animation/sound, direct-hit
Damage, blast ExplodeRadius) so it keeps its look even if the player
switches weapons mid-flight. Spawned from the camera along its full 3D aim
direction, offset projectileStartDist = 20 units ahead. Each frame it
steps forward by no more than projectileRadius (so a fast shot can't skip
a thin wall) and tests, in order: a shootable monster it has flown into
(projectileHitMobj — an axis-aligned radius box plus a vertical overlap,
id's PIT_CheckThing; the hit deals (P_Random%8 + 1) * def.Damage before
any blast), a wall/opening block (the same anyLineWithin machinery
collision uses, horizontal only), the floor/ceiling of the sector it's now
in, and whether it has left the geometry or exceeded projectileMaxRange =
8192. On impact it freezes (on the target itself for a direct hit, so the
blast is centred there) and plays through its ExplodeFrames sequence (each
held ExplodeTics tics) before removal. Explosion sprites draw at
explosionSizeMultiplier = 2.0 on top of ordinary distance scaling. The
rocket adds a 128u pRadiusAttack blast on top of its direct hit; plasma is
direct-hit only; the BFG adds aBFGSpray on top of its direct hit — every
shootable thing within missileRange, in a 90-degree fan in front of the
PLAYER (not the ball's landing spot) and in the player's line of sight,
takes (P_Random%8+1)*15 — the room-clearing effect the BFG is known for,
modelled as one hit per visible target in the fan rather than id's own 40
discrete rays (see attack.go's aBFGSpray doc comment for why that's
equivalent here).

Map objects (engine/mobj.go, info.go, states.go, spawn.go): a faithful
port of id's mobj/state model. A Mobj is any world object — monster,
projectile, pickup, decoration, corpse. MobjInfo (id's mobjinfo[]) is the
per-type template: doomednum, spawn health, radius/height, painchance,
MF_* flags, state links. states.go (id's states[]) is the animation FSM.
setMobjState (P_SetMobjState) enters a state, copies its sprite/frame/tics,
runs its action, chases through 0-tic states. spawnMapThings runs once at
level load: every THINGS entry that applies at Game.Skill (config skill,
default 3) in single-player becomes a Mobj via P_SpawnMobj, sat on the
sector floor (or hung from the ceiling for MF_SPAWNCEILING), angled from
the thing's angle, deaf bit -> MF_AMBUSH. Coverage: every Doom / Doom II
item and every static map decoration (columns, trees, torches and tech
lamps with their flicker, stalagmites, the evil eye, hanging bodies,
impaled bodies, gore, blood pools, the burning barrel). Monsters: all of
Doom 1 plus the Chaingunner and Hell Knight; the other Doom II monsters
(Revenant, Mancubus, Arachnotron, Pain Elemental, Arch-vile, Wolfenstein
SS, Commander Keen, Icon of Sin) are not ported, so those THINGS are
skipped. A separate playerMobj (not in the mobj list, never drawn) mirrors
the Camera each tic so it can be an AI target and a solid body. Game.Run
advances all mobjs on a fixed 35 Hz accumulator (runTic). Each render frame,
collectWorldObjects (engine/mobj.go) resolves every live mobj + in-flight
projectile into either a voxel instance (Game.Voxels has a model for the
sprite frame — section 20) or a camera-facing sprite billboard, for
render/worldgeo.Builder.AddVoxels/AddSprites to hand to the GPU — either
way shaded by the light level of the sector it stands in unless the frame
is fullbright. Each mobj is resolved at its start-of-tic position/facing
advanced toward its post-tic state by the fraction of a tic the wall clock
has run past the last one (interp.go — mobj.prevX..prevAngle, snapshotted
at the top of mobjTick), so a monster or an enemy fireball glides at the
display rate instead of stepping at 35 Hz while the player's own camera
moves every frame; a per-tic jump too large to be ordinary motion (a
teleport) is drawn at the new position uninterpolated. Presentation only —
collision, AI and pickups always read the exact post-tic fields.
collectGroundShadows (always on, no config gate — section 9) separately
lists every grounded mobj — skipping missiles, ceiling-hung and floating
things — plus the player, for world.frag's own floor contact-shadow pass.

AI (engine/enemy.go, noise.go, map.go, sight.go, attack.go, damage.go —
ported from p_enemy.c / p_map.c / p_inter.c). Monsters wake and hunt:
A_Look first checks whether a recent gunshot's sound reached its sector
(sectorSoundTarget), then, failing that, runs pLookForPlayers — a
line-of-sight trace (pCheckSight: segment vs. every linedef, one-sided or a
too-tall/short opening blocks; REJECT unused) plus a front-180-arc test
(a target behind the monster's back only registers within melee range).
The sound path is id's P_NoiseAlert / P_RecursiveSound (noise.go): every
weapon fire (beginFire) floods the shooter's sector outward through open
two-sided lines, marking each reached sector's soundTarget, so a monster
facing away or in the next room still wakes. The flood crosses at most one
ML_SOUNDBLOCK linedef (0x40) and stops at a closed door (no vertical
opening); soundTarget persists after the flood, matching vanilla's "one
shot wakes the whole connected area". A deaf (MF_AMBUSH, the thing's deaf
flag) monster ignores the sound and still needs line of sight. On waking a
monster plays its sight sound and enters the see state, whose frames loop
A_Chase. A_Chase turns the monster toward
its heading, then either attacks (checkMeleeRange / checkMissileRange gate
the per-monster attack actions — hitscan A_PosAttack / A_SPosAttack /
A_CPosAttack via pLineAttack, missiles A_TroopAttack / A_HeadAttack /
A_BruisAttack via pSpawnMissile, plus A_SargAttack melee and
A_SkullAttack's MF_SKULLFLY charge) or steps toward the target via pMove
-> pTryMove -> pCheckPosition (the generic per-Mobj clip: blocking lines,
ML_BLOCKING / ML_BLOCKMONSTERS, step-up <= 24, ledge-drop avoidance for
walkers, thing-vs-thing), re-choosing direction (pNewChaseDir, id's 8-way
diagonal-first search) when the current one is spent or blocked.

pDamageMobj applies, for the player, the config damageScale percent then
armour absorption; and, for a monster, a painchance roll into the pain
state, death/gib state selection at 0 / below -spawnhealth, corpse flags
(MF_CORPSE, drops MF_SHOOTABLE, height/4), monster item drops, and
infighting (a monster hit by another turns on it). At 0 player health it
calls killPlayer; pKillMobj bumps killCount. Missiles fly in mobjTick
(one whole tic per step) and detonate into their death state on a
wall/opening/thing hit, dealing (P_Random%8+1)*damage; pRadiusAttack does
the barrel/rocket blast. Every other (non-missile, non-charging) thing
gets mobjZClip in the same mobjTick: its Z is re-seated on its current
sector's floor, so a lift or crusher carries the things standing in it —
and when a ceiling has closed past a thing's head, crushMobj grinds it
(id's PIT_ChangeSector crush branch): a live MF_SHOOTABLE thing takes 10
damage every 4 tics with a blood spurt (so a crusher kills a monster, pops
a barrel), and a corpse still under the ceiling flattens once to a smear
(height 0, MF_SOLID cleared) then stops. Non-shootable décor is just shoved
down. The player is exempt here — its crush is the always-lethal
checkPlayerCrush below.
The player's bullet weapons trace through pLineAttack with a light
auto-aim. Randomness is a seeded PRNG stand-in for id's rndtable (no demo
compatibility; engine/random.go).

Player death (engine/damage.go): killPlayer(bigHit) fires at 0 health —
the player stops (you can still turn), horizontal velocity is zeroed, the
weapon lowers and DrawWeapon is suppressed, the eye sinks toward
deadViewHeight (8 units) over ~1s, the playerMobj drops MF_SHOOTABLE, and
DSPDIEHI/DSPLDETH plays. The status-bar face goes to STFDEAD0. There is no
respawn — playerDead clears only on the next level load. crushPlayer() /
checkPlayerCrush() (run from runTic): when a sector's floor-to-ceiling gap
drops below playerHeight - 1 the player is crushed — instant death,
bypassing config damageScale, from a closing door, a crusher ceiling or a
rising floor.

Pickups (engine/pickup.go, ported from p_inter.c): each tic
checkItemPickups looks for an MF_SPECIAL thing the player's body overlaps
(id's reach test: the item's base at most toucher->height above, at most 8
units below) and runs pTouchSpecialThing. The overlap test is SWEPT: it
matches an item whose radius the player's body covered at the sample point
OR anywhere along the segment from the previous sample — the check runs at
35 Hz but the camera moves every render frame, so a point-only test
dropped items run across between tics. A move longer than pickupSweepMax
(~96 units) is treated as a teleport and only the end point is tested.
pTouchSpecialThing handles armour (green/blue set 100/200, refuse if
already at/above; helmet bonus +1 to a 200 cap), health (stimpack/medikit
refuse at >=100 and cap there; bonus vial +1 to 200; soul +100 to 200;
mega sets 200 + blue armour), the six timed powers (Powers[], counted
down by updatePowers; invisibility toggles the player's MF_SHADOW), keys
(always consumed in single-player), ammo (giveAmmo, clip sizes, maxammo
clamp, half from a dropped clip; a box is 5 clips), the backpack (doubles
MaxAmmo once, then a clip of each), and weapons (giveWeapon: grant, plus
two clips of its ammo for a found weapon / one for a monster-dropped one;
switch to it if new, when config switchWeaponOnPickup is set). Health/armour
changes mirror onto the player mobj. DefaultPlayerStats is a real Doom
start — 100 health, pistol, 50 bullets. A health or armour pickup while
already at the cap correctly does nothing (vanilla); TPF_PICKUP_DEBUG=1
logs a per-item line of what each touch did. An active invulnerability
sphere cancels any sub-1000 hit in pDamageMobj.

Line/sector specials (engine/specials.go, spec.go, switches.go — ported
from p_spec.c and friends). Every active mover or light animation is a
sectorThinker stepped by tickSpecials on the 35 Hz tic, writing
Level.Sectors[i] heights/light in place (one height mover per sector at a
time — sectorActive). Thinker types: vldoor (raise / open-stay / close /
close-wait-open, blazing), floorMove (lower/raise to
lowest/highest/next/8-above/by-N), plat (lift down-wait-up, perpetual,
raise-and-change), ceilMove (lower-to-floor, crush-and-raise),
lightThinker (flicker / strobe / glow / fire), scroller (special 48/85).
activateLine dispatches the vanilla special numbers by trigger class (walk
/ switch / gun), runs the effect over findSectorsFromTag, then clears a
non-repeatable ("1") special; changeSwitchTexture flips SW1<->SW2 in the
live sidedef (the wall pass renders it flat, section 20) and schedules the
flip-back for a repeatable switch. checkCrossedSpecials fires walkover
lines the player steps over; a hitscan that hits a wall fires its gun
special. evTeleport (specials 39/97/125/126) moves the mobj to the sector's
MT_TELEPORTMAN and sets Mobj.TeleportFreeze = teleportFreezeTics (18, ~1/2
s); while it's positive evTeleport refuses to move that mobj again, so a
landing pad walled in by teleport lines can't fire you straight back before
you walk clear — long enough to step off a cramped pad, short enough not to
block a deliberate back-to-back chain. A monster's freeze counts down in
mobjTick; the PLAYER's mobj isn't in g.mobjs, so runTic's player-sync block
decrements it there — without that it stuck at 18 and a WR pad only ever
worked once.
spawnSpecials starts the always-on light thinkers and counts secret
sectors; playerInSpecialSector applies damage floors (5/7/16/4/11) and
secret discovery (9) each tic. Level exits (11/51/52/124 -> exitLevel)
trigger loadNextMap (engine/level.go): reload the map, keep
weapons/ammo/health, drop keys/powers, reposition at the new player start;
OnLevelChange restarts the music. A_BossDeath on the Baron's final frame
drops a tag-666 floor on E1M8; the MAP07 tag-667 and ExM8 boss arms are
transcribed but dormant because those monster types aren't ported.

Animated flats and wall textures (engine/animtex.go — id's P_InitPicAnims
plus BOOM's ANIMATED lump). The table is the classic Doom / Doom II set:
the liquid flats (NUKAGE1..3, FWATER1..4, LAVA1..4, BLOOD1..3, SLIME01..12,
RROCK05..08) and every animated wall texture (BLODGR/SLADRIP/BLODRIP fire
and gore, FIREBLU/FIRELAVA/FIREMAG/FIREWALL, GSTFONT, ROCKRED,
BFALL/SFALL/WFALL, DBRAIN). A WAD that ships an ANIMATED lump replaces the
built-in table with its own rows (23-byte istexture/end/start/speed
records) — how a Boom/MBF PWAD defines custom animations. Each range
expands to an ordered frame list: by stepping a trailing digit where the
names have one, otherwise by walking texture-definition order (walls) or
WAD directory order (flats); a range with any frame the WAD doesn't ship
is skipped. initTexAnims snapshots each sector's authored flat and each
sidedef slot whose texture is an animated frame; animateFlats +
animateWalls (from runTic, after tickSpecials) rewrite the live name in
Level.Sectors[i] / Level.Sidedefs[i] every tic to
`frames[(levelTime/speed + startIndex) % n]` — id's translation-table
formula, so two surfaces that begin on different frames stay a step out of
phase. Stateless (recomputed from levelTime); the renderer resolves the
new name through the usual Flat / WallTexture cache.

ZDoom ANIMDEFS (engine/animdefs/ clean-room text parser; engine/animdefs_
load.go + engine/animwarp.go the glue) layers on top. `flat` / `texture`
blocks become animDef rows appended after the built-ins (so an ANIMDEFS
entry for a name overrides the list animation for it, since initTexAnims
keys groups by frame name, last write wins): `pic <n|name> tics <t>` gives
per-frame durations (texAnimGroup.durs + a running-sum prefix table;
frameFor walks it instead of the uniform `/speed`), `rand a b` is
approximated by the midpoint to stay stateless, `oscillate` ping-pongs the
frame+dur lists, `range <name> tics <t>` is the short uniform form. `warp`
/ `warp2 flat|texture <name> [speed]` is BAKED: at level load each warped
texture is expanded into warpPhases (32) pre-distorted copies (sine offset
per axis, nearest+wrap, warp2 = 2x amplitude / half period), Inject()ed
into assets.Textures under `~WRP<n>_<pp>` names, and registered as a normal
swap-frame group keyed by the base name — so the swim shows identically on
both renderers with zero shader/rasteriser changes, capped at warpDefLimit
(24) warped textures. `switch` / `cameratexture` / `animateddoor` /
`#include` are skipped with a logged warning. ANIMDEFS lumps are read from
the WAD + mounted mods (assets/mods/ANIMDEFS), parsed once and cached on
the Game. assets/mods/ANIMDEFS.example documents the syntax.

ZDoom TEXTURES (engine/texturedefs/ clean-room parser; engine/texturedefs_
load.go the glue; assets/texturesdef.go + _compose.go the compositor).
Text-defined composite textures: `Texture` / `WallTexture` / `Flat` /
`Sprite` / `Graphic` blocks carry `XScale` / `YScale` / `Offset` /
`WorldPanning` / `NullTexture`, and `Patch` sub-blocks carry `FlipX` /
`FlipY` / `Rotate 90|180|270` / `Alpha` / `Style` (copy / translucent /
add) / `Blend`. loadTextureDefs (from NewGame, before spawnSpecials)
gathers TEXTURES from the WAD + mods, converts to assets.ZDDef and calls
Textures.AddTextureDefs. A registered name is COMPOSED on first
WallTexture/Flat/Sprite resolution (orientRGBA rot+flip, blendTintRGBA,
compositePatch) and shadows the WAD's own decode plus any hi-res / Quake
override — ZDoom's "last TEXTURES wins". XScale becomes the resolved
bitmap's TexelsPerUnit, so a drop-in higher-res wall samples at the
authored density instead of the old width-ratio guess; NullTexture
resolves like "-". Patch sources resolve composite -> patch lump -> flat
lump (depth-limited against cycles). `Translation` and the exotic styles
are parsed but approximated / skipped with a warning.
assets/mods/TEXTURES.example documents the syntax.

Hardware-path animated-texture fix (same round): the GPU-geometry builder
caches static geometry with texture bindings baked in and only rebuilt it
when a SECTOR HEIGHT changed (worldGeomChanged), so animated flats/walls —
built-in, ANIMATED, ANIMDEFS and warp alike — were frozen on frame 0 on
that path. renderFrame now also calls animFrameChanged() (an FNV hash of
every animated surface's current live name, changing exactly on the tics an
animation steps) and Invalidate()s the builder then.

Dynamic lights (engine/lights.go, engine/maplights.go) — everything beyond
world.frag's sector fade. Two kinds:
  Dynamic (lights.go, collectLights): the player's warm muzzle-flash light
  while firing, a per-weapon colour on each in-flight rocket/plasma/BFG with
  an explosion flare that ramps then fades — and the enemy equivalents:
  every MONSTER projectile in flight (missileLight — imp orange, caco
  blue-violet, baron/knight green; white-hot and wider for the few impact
  tics), and a monster's muzzle flash while it fires a hitscan
  (monsterFlashLight — former human / shotgun guy / chaingunner, keyed off
  the current state being full-bright). All are interpolated to the sprite
  position, gameplay-critical, always kept, and the only lights that cast a
  screen-space contact shadow.
  Static map emitters (maplights.go, buildStaticLights, rebuilt per level
  after spawnSpecials + spawnMapThings): one light per light-animation
  sector — at its centroid, its intensity/radius re-read from the LIVE
  Level.Sectors[i].LightLevel each frame, so a strobe or flicker sector
  visibly pulses a real light — and one per emissive decoration (torches
  by colour, burning barrels, tech lamps, candelabra, the evil eye), flame
  ones getting a cheap deterministic wobble (flickerWobble off levelTime).
  appendMapLights pre-culls each by a precomputed squared reach (cullR2 —
  skips the sector lookup + wobble for anything far) and by the view
  direction (an emitter well behind the camera reaches no visible pixel bar
  a water reflection but would still cost the shader a per-pixel iteration),
  samples the survivors, and keeps the nearest up to activeLightBudget (40)
  total. Both cuts are RAMPED, not hard: a light is admitted from
  radius+mapLightCullMargin (512) out but its intensity is scaled 0->full
  over the outer mapLightFadeBand (224) as the camera closes, and the last
  mapLightRankFade (6) budget slots are dimmed toward the cut — so a torch
  fades in as you approach instead of snapping on the instant you cross its
  cull sphere, and which lights make the nearest-N cut can shift frame to
  frame without a pop. The per-pixel (1-(d/R)^2)^2 shader falloff was
  always smooth; this fixes the CPU-side include/exclude discontinuity.
  GLDEFS (engine/gldefs/, engine/gldefs_load.go): a GLDEFS (or DOOMDEFS)
  lump — the ZDoom/GZDoom/UZDoom dynamic-light format — from the loaded WAD
  and/or from a mod mounted under assets/mods/ (§3) defines named lights and
  attaches them to sprite frames via object{frame{light}}; those override
  the built-in decoration table. engine/gldefs is a clean-room, pure-Go
  reader of that text format (no GZDoom source — the ports are GPLv3, this
  reimplements only the documented data format); it handles pointlight /
  pulselight / flickerlight / flickerlight2 / sectorlight, #include (resolved
  against the WAD then the mods), and captures brightmap blocks for later.
  Lights are indexed by sprite name + frame letter, so no GZDoom-actor-class
  table is needed: buildStaticLights looks up spriteNames[mo.Sprite] +
  mo.Frame and, on a hit, emits those lights instead of the decoLights
  entry. Game.projectileLight does the same for an in-flight rocket/plasma/
  BFG — a GLDEFS light on the FLYING sprite's frame overrides the built-in
  ExplodePrefix colour (the exploding flare keeps its hand-tuned ramp).
  loadGLDefs assembles the lump(s) in load order (WAD first, mods
  after); loadMods (engine/mods.go) builds the mount stack. A plain IWAD
  with no GLDEFS lump and no mod is unchanged — the built-in table stands.
  assets/mods/GLDEFS.example is the project's own decoration-light tuning in
  GLDEFS form; rename it to GLDEFS to activate.

  UMAPINFO (engine/mapinfo/, engine/mapinfo_load.go): the community per-map
  metadata lump (a small vanilla-friendly subset of ZDoom MAPINFO — full
  MAPINFO is not read). loadMapInfo assembles every UMAPINFO lump (WAD then
  mods) and engine/mapinfo.Parse — a clean-room, lenient reader (unknown
  keys kept in Entry.Raw, a bad value reported but parsing continues) —
  turns it into name->*Entry. Wired: `levelname` (Game.levelDisplayName, the
  debug-HUD line + the "entered" log), `music` (Game.MapMusicLump, tried
  first by cmd/engine's audio.PlayLevelMusic call), `skytexture`
  (Game.ApplyMapInfo -> worldgeo.Builder.SetSkyName — section 10), `next` /
  `nextsecret` / `endgame` (nextMapName
  consults them before the ExMy/MAPxx default progression; a target not in
  the WAD falls back), `partime` (Game.parTime). Every other key
  (label, levelpic, intertext, bossaction, exitpic, ...) is parsed and
  retained but not yet acted on. A plain IWAD has no UMAPINFO — nothing
  changes. assets/mods/UMAPINFO.example shows the format; rename to
  UMAPINFO to activate.

  DEHACKED / BEX (engine/dehacked/, engine/dehacked_load.go): the classic
  patch format that retunes the internal tables. engine/dehacked is a
  clean-room lenient line parser (Thing/Frame/Weapon/Ammo/Sound/Pointer
  numbered blocks, [STRINGS]/[PARS]/[CODEPTR]/[SPRITES] BEX sections,
  old-style `Text a b` byte subs, header lines) -> a Patch of plain maps
  keyed by DeHackEd's fixed numbering. loadDehacked reads a DEHACKED lump
  from the WAD / mods. engine/dehacked_tables.go carries id's mobjtype_t
  order (Thing 1..79) + the MF_* flag-name map (data-format facts, not
  behaviour). engine/dehacked_states.go carries id's full statenum_t (967
  entries, verified byte-for-byte against chocolate-doom's info.h by
  TestDoomStateAnchors) + spritenum_t (138) as sequence-helper-built name
  lists, plus dehState / dehSprite translating a DeHackEd number to this
  build's stateNum / spriteNum (ok=false for psprite frames and
  unimplemented Doom II actors). APPLIED: Thing STAT fields (Hit
  points->SpawnHealth, Speed, Width/Height->Radius/Height undoing the
  /65536 fixed point, Mass, Missile damage, Reaction time, Pain chance,
  ID #, Bits->Flags); Frame edits (Sprite number->dehSprite, Sprite
  subnumber -> Frame + fullbright via the 0x8000 bit, Duration->Tics,
  Next frame->dehState); [CODEPTR] and old-style Pointer/Codep-Frame
  action edits (dehActionByName covers the ~18 codepointers this build
  implements; anything else logs and is skipped); BEX [SPRITES] and 4-char
  Text substitutions -> live spriteNames[] rename; [PARS] (Game.dehPars ->
  parTime), [STRINGS] level names (HUSTR_E1M1 / HUSTR_1 / P|THUSTR_n ->
  Game.dehLevelNames -> levelDisplayName). The tail (dehacked_misc.go):
  [MISC] -> a dehMisc struct (lazily defaulted via g.dm()) threaded into
  giveBody / soulsphere / megasphere / giveArmor (pickup.go) and
  iddqd/idkfa/idfa (cheats.go), plus BFG Cells/Shot -> Weapons[wpBFG]
  .AmmoCost and Initial Health/Bullets retro-patching a fresh g.Player;
  numbered Weapon N -> Weapons[N].AmmoType / AmmoCost (Ammo type, Ammo per
  shot); numbered Ammo N -> dehMaxAmmo[N] (Max ammo) + clipAmmo[N] (Per
  ammo); [CHEAT] -> g.cheatOverride, so cheats.go matches g.cheat("iddqd")
  and a blank patch value disables a code. NOT wired: numbered Sound N
  blocks (this build plays sound lumps by name — no sfxinfo_t table) and
  weapon-frame pointers (separate WeaponFrame table) — logged.
  Liquid glow (engine/liquidlights.go, appended by buildStaticLights): every
  lava sector seeds one or more warm-orange flickering point lights at
  sampled interior points (1 for a small pool, up to a 2x2 grid for a big
  lake), sized to the sector, so lava throws light on the walls and things
  around it; every nukage/slime sector seeds a dim sickly-green light so a
  toxic room reads green in the dark. Classified by the floor flat's family
  prefix (LAVA*/FIRELAVA, NUKAGE*/SLIME*), capped at maxLiquidLights (64)
  per level, thin trim strips skipped (it is just more render.Lights).
  Water and blood seed nothing.
collectLights and appendMapLights reuse per-frame scratch buffers, so the
whole per-frame light gather is allocation-free. game.go's renderFrame
passes the merged list (dynamic first, and how many are dynamic so
world.frag knows the shadow-casters) straight to DrawWorld (section 9).

Sound (engine/sound.go): loadSound decodes and caches a DS* lump by name
(nil-cached on failure/absence); playSound is a nil-safe fire-and-forget
wrapper Game never checks before calling. playWeaponSound is the same but
routed through audio.Device.PlaySoundVol with g.weaponVolume (config
weaponVolume) — every gun's fire/reload noise and the chainsaw idle whir
go through it so they can be turned down against the rest of the SFX.
playWorldSound is the equivalent for the level's own machinery — doors,
lifts/platforms, moving floors and ceilings/crushers, stairs, switch
clicks, teleporters (every playSound call in specials.go/switches.go and
the door/teleport ones in spec.go) — scaled by g.worldVolume (config
worldVolume, default 0.5). Several of those loop while a sector moves
(DSSTNMOV every 8 tics, perpetual-lift DSPSTART/DSPSTOP), so a busy map's
background drone is turned down without touching weapon, monster or pickup
SFX. sfxHook is a test-only observation point for every playSound /
playWeaponSound / playWorldSound call, never set in a real run.

16. KNOWN LIMITATIONS
--------------------
Behaviour a reader is likely to hit that is intentional or simply not
built:

  - Doom II monsters: only the Chaingunner and Hell Knight are ported. The
    Revenant, Mancubus, Arachnotron, Pain Elemental, Arch-vile, Wolfenstein
    SS, Commander Keen and Icon of Sin are not, so those THINGS don't
    spawn — a Doom II map plays, just with fewer monsters in the rooms
    that rely on them. The MAP07 tag-667 and ExM8 boss-arm hooks are
    transcribed but dormant for the same reason.
  - Spectres (MF_SHADOW) render as ordinary shaded sprites/voxels — the
    vanilla "fuzz" distortion isn't reproduced.
  - Player death has no on-screen "press use" prompt and no death
    view-roll, but pressing E while dead restarts the current level
    (fresh loadout). There are no intermission / tally screens (killCount,
    secretCount, totalSecrets are tracked, nothing displays them), and no
    on-screen pickup / locked-door messages.
  - The player's fall arc is tuned MORE generous than vanilla (softened
    gravity + a one-time takeoff kick on a committed run-off, ~1.6x the
    vanilla-gravity reach) so gaps between raised platforms are clearable.
    There IS a jump key now (Space, section 15) — non-vanilla; no knockback
    launch, no smooth step-up lerp. Monsters, corpses and items don't fall —
    mobjZClip pins every ground thing to its sector floor each tic;
    MF_NOGRAVITY floaters and MF_SPAWNCEILING decorations are exempt.
  - Line-special coverage (activateLine) spans every vanilla number the
    DOOM / DOOM II IWADs use. Several "…and change texture/type" and
    "raise by shortest lower texture" variants (9 donut, 14/20/30/47/59,
    15/143) run their motion but skip the texture/type swap; unrecognised
    numbers are logged and ignored.
  - The hi-res override set (section 11) covers only names DOOM1.WAD itself
    defines — Doom II or another PWAD's own names render at normal WAD
    resolution.
  - HD weapon pack (section 11): a frame whose weapon the loaded IWAD ships
    no sprite for (SSG/plasma/BFG under shareware) gets a synthesised
    hotspot, so its muzzle-flash overlay is only approximately aligned. The
    gun itself is fine, and a retail IWAD gives every frame its real
    hotspot.
  - Only F_SKY1 is recognised as the sky flat (a sky FLOOR, and the
    per-linedef sky-transfer specials 271/272, aren't handled). The per-map
    sky *texture* pick does follow PrBoom (SKY1..4 by episode / MAP range —
    section 10). The external Mars skybox panorama that used to override it
    is currently not wired into the hardware renderer at all (section 10) —
    every level shows its own WAD sky texture regardless of whether
    assets/skybox/mars_sky.png is present.
  - Resize/monitor-change recreates the Vulkan swapchain, but the render
    resolution is fixed at startup — a resize rescales the same internal
    frame via the letterbox blit, it doesn't re-render at the new size.
  - Hardware-renderer lighting: a light-animation sector emits ONE point
    light at its centroid, not an area source, so a big or oddly-shaped
    bright sector lights unevenly. The only shadowing is a screen-space
    depth march (worldambient.frag, section 9), and only for the leading
    dynamic + up to two nearest static lights; an occluder outside the
    frame casts nothing, and thin geometry can leak. No thing-on-wall or
    thing-on-thing shadow, no real shadow maps (that needs a shadow atlas,
    not yet built). The shader loops up to activeLightBudget (40) lights
    per pixel; a very torch-dense room still spends real GPU time.
    cartoonOutlineStrength / cartoonLightBands and the bloom/SSAO/god-ray
    tuning constants are fixed in render/vulkan/world.go and worldambient.go,
    not player knobs (lightScale, ambientLight, exposure, cartoonShading
    are config — section 17).
  - The COLORMAP lump is not read — its effect is reproduced directly in the
    shader (section 9). The only thing that raises ExtraLight today is the
    Heretic Torch/Tome artifacts (section 24); the flashlight is a real spot
    cone instead (section 14), and a weapon-flash room-brightening hook is
    wired but unused.
  - cmd/isoengine (section 23) has no intermission flow of its own, reuses
    cmd/engine's HUD styles as-is, uploads voxel meshes lazily (a brief
    first-sight hitch, unlike cmd/engine's warm-up), and draws no ground
    shadows. It shares every other engine limitation in this list.
  - Heretic (section 24) is a full playable game — the monster roster (Doom
    AI reused) incl. the three bosses, the eight weapons + Tome-of-Power
    powered modes + six ammo types, the ten inventory artifacts (Enter
    uses, [ / ] cycle), the status bar, wind sectors, decorations, keyed
    doors, sky, liquids, sounds, music, voxels. Not modelled: a chicken-
    morph PLAYER state, the bosses' signature moves (whirlwind / charge /
    two-phase), the episode-end story screens; ghost monsters read as dim
    rather than fuzzed.
  - Plasma Rifle / BFG9000 sprite and sound lump names are transcribed
    from documentation — the shareware IWAD has no Plasma/BFG assets to
    verify against. A few death/attack-chain tic counts are
    close-but-not-exact vanilla.
  - Level music resolves via wad.MusicLumpName: "D_ExMy" for Doom, the
    fixed per-slot table for Doom II / Final Doom MAPxx, then a "D_"+mapname
    fallback for PWADs. No MUSINFO / MAPINFO remapping.
  - Music: Windows and Linux use libfluidsynth + a GM soundfont
    (cgo-loaded on Windows, purego on Linux), rendered pull-mode into the
    shared mixer; Windows falls back to winmm's GS Wavetable synth when no
    DLL/soundfont is present; macOS/BSD have no backend yet and run silent.
    See sections 13 and 21.
  - Sound effects run through one PrBoom-style software mixer on every
    platform — a single 48 kHz S16 stereo oto stream, per-clip linear
    interpolation from 11 kHz, master gains + hard clip, shared with the
    music synth (audio.go, mixer.go). See section 13.


17. PACKAGE config — RUNTIME SETTINGS
------------------------------------
config.Load() reads an optional config.json into a flat struct. find()
looks in the working directory first, then in the executable's own
directory and up to three parents of it — so bin\engine.exe picks up a
config.json in the repo root whether launched from the root, from bin\, or
by a double-click. Load is forgiving: a missing file, a malformed file, or
any single out-of-range field falls back to the baked-in default for that
part and logs it, never fails startup. cmd/engine then logs one "config in
effect — ..." line with every resolved value.

A partial config.json is fine — any key you leave out uses its default —
but it's easier to work from a complete file. `go run ./tools/genconfig`
writes one (config.DefaultJSON: Default() marshalled with every key; a
test asserts it stays in sync with the struct). When a file IS loaded but
missing keys, Load logs exactly which options are falling back to defaults
and points at genconfig, so a newly-added option is visible rather than
silent.

The pre-game launcher (section 22) is the normal way to edit this file:
every key below is one row of its settings panel, and Play writes the
result with config.SaveMerge — a key-preserving merge that rewrites only
the keys the launcher manages, leaving comments and any unknown keys in an
existing config.json intact. launcher/fields.go is the launcher's table of
these keys; a test asserts it covers every Config field, the same guard
tools/genconfig has. The full key list:

  resolution     FULL-SCREEN render size — "540p" (960x540), "600p"
                 (800x600), "720p" (1280x720, default), "900p" (1600x900),
                 "1080p" (1920x1080), "1440p" (2560x1440), or "native"
                 (the monitor's framebuffer). Case-insensitive. In
                 full screen a preset above the monitor is capped to the
                 monitor unless renderScale > 1. Not consulted at all in
                 windowed mode.
  renderScale    multiplies whichever base applies (the resolution preset
                 full screen, the window size windowed) on both axes;
                 clamped [0.25, 2.0], default 1.0. 0.5 = render a quarter
                 of the pixels and let the GPU upscale; > 1 = supersample.
                 The single biggest performance lever the renderer has.
  windowed       false (default) = borderless fullscreen on the primary
                 monitor, rendered at `resolution` (section 12); true = a
                 normal resizable window, rendered at the window's own size.
  windowWidth /  the windowed-mode window size AND its render resolution
  windowHeight   (ignored for fullscreen); default 1280x720.
  fovDegrees     horizontal FOV at the 16:10 reference aspect; clamped
                 [70, 130], default 100. Wider display aspects widen the
                 view Hor+ (section 8), they don't stretch it.
  hudScale       size multiplier for the status bar and the debug text.
                 1.0 (default) = the authored proportions filling the screen

  weaponScale    size multiplier for the first-person weapon viewmodel,

  vsync          true (default) = tear-free FIFO present; false = mailbox
                 (uncapped, low-latency) when the driver offers it.
  maxFPS         frame-rate cap (a sleep at end of frame) used when vsync
                 is off; 0 (default) = uncapped. Harmless with vsync on.
  [As of the software-rendering removal (see that section below):

                 light are summed, a wall/flat/sprite never reads darker

                 lit room stays legible instead of fading toward black,
                 while a monster in a genuinely dark sector still needs a
                 real light (torch, muzzle flash, the flashlight). Clamped
                 [0, 1], default 0.2. 0 reproduces the old crush-to-black

  exposure       final multiply on the HDR colour before the tonemap;

  cartoonShading false (default): world.frag's fade() posterizes its 0..1

                 black (cartoonOutlineStrength 0.85). Both are fixed
                 constants in render/vulkan/world.go, not sub-knobs. In the
                 launcher it sits in the top bar next to the WAD/level
                 pickers, not the scrolling list.
  fogColor       distance-fog colour, hex "RRGGBB" (a leading '#' is
                 allowed). Empty (default) = no fog. An unparseable value
                 logs and disables fog.
  fogDensity     exponential distance-fog strength: a pixel is blended
                 toward fogColor by 1 - exp(-fogDensity * cameraDistance)
                 (map units). 0 (default) = off; clamped to [0, 0.02].
                 ~0.0006 is a light haze, ~0.003 a heavy murk. Fog only
                 applies when BOTH fogColor is set and fogDensity > 0,
                 computed in world.frag. The sky is never fogged.

Config.RenderSize(windowed, fbW, fbH) produces the pixel size handed to
raster.New and vulkan.NewWorld: windowed -> the window's framebuffer (fbW/fbH);
full screen -> the resolution preset, capped to fbW/fbH when renderScale
<= 1 ("native" is fbW/fbH directly); then renderScale on top. So a
windowed run renders exactly at the window size with no rescale on
present, and full screen renders at `resolution` (never above the
monitor unless you ask for supersampling) letterboxed to the screen. The
Vulkan validation layers are the env-only TPF_VK_DEBUG switch (section 9);
the exit-pause is the env-only TPF_NO_PAUSE switch (section 2).


18. EXECUTABLE SIZE & PERFORMANCE
-------------------------------
Two deliberate, independent choices — one for the exe's size, one for its
runtime CPU cost.

Size. The hi-res skybox and wall/flat/sprite textures (sections 10-11)
load from disk rather than being compiled in via go:embed. Baking ~22 MB
of PNGs into every copy of the executable is exactly the bloat a shipped
game avoids by putting large data in loose asset files beside the exe —
the same reason essentially every commercial game (including the original
Doom, whose engine and IWAD were always separate files) ships that way.
With `-ldflags="-s -w"` on top (section 2) the release build is ~3.65 MB;
embedding the assets instead would put it near 31 MB.

CPU. Level geometry doesn't move, so spatial queries are answered against
indices built once at level load, not by rescanning the level:
  - collisionGrid (engine/collisiongrid.go) buckets Linedef indices into
    128-unit cells in NewGame (never rebuilt — doors animate a Sector's
    ceiling height, not any Linedef's position). anyLineWithin visits only
    the lines in cells overlapping the query radius. Every tryMove makes
    up to three anyLineWithin calls (full, X-only, Y-only) per frame, plus
    one per in-flight projectile.
  - The same grid answers SEGMENT queries (forEachAlongSegment): it walks
    the cells a ray/segment crosses, work proportional to the segment's
    length in cells, not its bounding-box area. The monster line-of-sight
    trace (every monster every tic), the hitscan wall trace, and the
    walkover-special check on each player move all use it. Both grid
    queries yield a superset — callers still run their own precise
    intersection test per candidate.
  - sectorindex.go precomputes, once per level, immutable after:
    sectorLines[s] (linedefs touching sector s) and sectorNeighbors[s]
    (sectors sharing a two-sided line with s). The p_spec.c
    surrounding-sector queries iterate only the true adjacency;
    EV_BuildStairs in particular drops from O(sectors x linedefs) per step
    to O(lines touching this sector).

The GPU does the actual per-pixel work now (section 9); the CPU side's job
each frame is building/maintaining the triangle list and culling what the
GPU doesn't need to see. What is done about that:
  - Static-geometry visibility culling (render/worldgeo/visgrid.go): the
    colour pass skips a static Draw whose real bounding box fails a
    per-frame camera-vs-FOV test, and shares more textures back-to-back for
    fewer descriptor rebinds.
  - NOT re-Invalidate()ing the whole static vertex buffer on a mid-glide
    frame whose interpolated sector height rounds to the same int16 as
    last frame (renderedSectorHeightsChanged) — it was forcing a full-level
    walk + a blocking GPU re-upload every frame a door moved.
  - Moving SSAO's disc gather and the god-ray march off full-res pixels
    into one quarter-res worldambient.frag pass (1/16 the pixel count, plus
    a 3x3 AO denoise).
  - assets.Textures' wall/flat/sprite decode cache (section 7) takes only a
    read lock on the (overwhelmingly common) cache-hit path, so the several
    goroutines that resolve textures while the static geometry builds don't
    serialise against each other for a lookup that's just a map read.
  - Render resolution is the crude but decisive lever: config's
    resolution / renderScale set how many pixels the GPU touches per frame.
  - maxFramesInFlight is 2, so the CPU can build/record the next frame's
    command buffer while the GPU is still presenting the last one.
engine/game.go + iso_render.go log a per-stage (sim / build / draw) smoothed
frame-timing line alongside the visibility stats so the next stall is
locatable — sim is gameplay (Systems + the 35Hz tic), build is the CPU-side
BSP walk / geometry prep / visibility culling, draw is DrawWorld's command
recording + submit + whatever fence wait it hits catching up to the GPU;
splitting them apart is what tells "a slow OS/driver" apart from "this
engine's own code got slower."

20. VOXEL MODELS
---------------
Map objects — monsters, items, ammo, keys, the corpses and gibs they leave
— can be drawn as voxel models instead of flat sprites, from a voxel pack
in assets/voxel/. The engine ships none; supply Cheello's "Voxel Doom"
Doom1_Voxel.pk3 and Doom2_Voxel.pk3 (or another KVX pack in the same
layout). They're gitignored — a derivative of id's sprites with their own
terms. Absent, or `voxels false` in config.json, the game just uses
sprites.

Loading. cmd/engine picks reikallhereticvoxels.pk3 for a Heretic IWAD
(section 24), Doom2_Voxel.pk3 when the start map is a Doom II MAPxx, else
Doom1_Voxel.pk3, and calls assets.LoadVoxelPackDir — which finds the
assets/voxel directory next to the working directory or the exe and reads
the .pk3 (a zip):
  - VOXELDEF (assets/voxeldef.go) — the def lump, named either "VOXELDEF.txt"
    (the Doom packs) or "VOXELDEF" (reikall's Heretic pack). One entry per
    line, `<sprite><frame> = "<basename>" [{ AngleOffset = N  Scale = f }]`,
    e.g. `trooa = "trooa" {}` maps sprite TROO frame A to voxels/trooa.kvx.
    A bare 4-letter key (`akyy = "akyy"`) means "every frame of that sprite"
    — stored as "<sprite>*" and picked up by VoxelSet.Model's whole-sprite
    fallback (Heretic keys / some artifact pickups). `spin` /
    `overridepalette` / `pivot` and other unknown props are ignored. C-style
    /* */ blocks (disabled entries) and // line comments are stripped first.
    The D2 pack keeps everything under filter/doom.id.doom2/; path.Base
    collapses that away.
  - KVX (assets/kvx.go, decodeKVX) — Ken Silverman's voxel format: an
    int32 mip-0 length, then that mip (xsiz/ysiz/zsiz, xpivot/ypivot/zpivot
    in 8.8 fixed point, an int32 xoffset[xsiz+1] table, an int16
    xyoffset[xsiz][ysiz+1] table, then run-length "slab" bytes), any lower
    mips (ignored), then a trailing 768-byte palette. Only mip 0 is kept.
    The palette is VGA 6-bit in every Doom voxel pack, so it's scaled to
    8-bit. A slab is `ztop, zleng, faceflags, colour[zleng]` — a vertical
    run of surface voxels; KVX already omits fully-occluded interior
    voxels, which is what keeps a monster at a few thousand voxels.
Every referenced model is decoded up front (~120 models, a few MB) so the
render path is lock-free with no mid-game decode hitch. VoxelSet.Model(
spritePrefix, frame) is a plain map lookup keyed by the lowercase
"<prefix><a+frame>" string the engine builds from spriteNames[mo.Sprite]
and mo.Frame.

Rendering is real GPU geometry, not a CPU splat: render/worldgeo.
BuildVoxelMesh (once per model, cached — section 9) turns a KVX model into
a static vertex-coloured cube-face mesh, and a dedicated voxel.vert/frag
pipeline draws one instance per visible voxelized thing inside the world
pass, depth-sorted against the level geometry like anything else. Per
frame, engine.Game.collectWorldObjects (engine/mobj.go) resolves each live
mobj to a worldgeo.VoxelInstance when Game.Voxels has a model for its
current sprite frame, else a sprite billboard (section 8's ThingSprite) —
there is no on-screen-size cutoff any more; a model far enough to be tiny
just draws as a tiny mesh, the same way a distant sprite draws small.
  - Yaw is (thing angle + VOXELDEF AngleOffset + voxelKVXFrontBias — the
    last a fixed -90 degrees, engine/mobj.go, backing every KVX model's
    built-in "front" a quarter turn to line up with a Doom thing's facing;
    tune per-pack via AngleOffset, not this constant). Things stay upright
    (no voxel pitch/roll).
  - Scale is config voxelScale (default 1.0, map units per voxel —
    Cheello's pack is authored 1:1 with Doom units, an imp's model is ~57
    voxels tall) times the VOXELDEF entry's own Scale multiplier.
  - Shading is world.frag's normal per-pixel model (section 9): the
    thing's real sector light plus every dynamic light in range, not a
    single flat multiplier for the whole model. A fullbright frame skips
    the sector-fade term.
Every static decoration and every Doom 1 / Doom II item spawns and
voxelizes; the missiles/projectiles the pack comments out, and the Doom II
monsters not yet ported (section 16), never reach the renderer.

Wall switches. There is no procedural 3D switch relief: switches render as
their flat wall texture like any other wall (the normal wall pass), and
pressing one swaps its SW1 texture for SW2 (or back) in place —
engine/switches.go's
changeSwitchTexture writes the new name straight into the live sidedef,
so the wall pass shows it the next frame (section 14). Voxel models
(above) and the flat switch textures coexist fine; the switch just isn't
a 3D object.


21. PORTABILITY & PORTING TO ANOTHER OS
--------------------------------------
The target is: on any OS with a Vulkan driver, a port is a handful of
clearly-isolated files, and nothing else. Windows and Linux have both been
run; macOS has not, but the codebase is already arranged for it.

WHAT IS ALREADY PORTABLE (no OS code in it)
  - wad, bsp, assets, raster, render, config, and the tools/ commands are
    pure Go with no build tags — they cross-compile to any GOOS as-is
    (verified with `GOOS=linux go build` on those packages).
  - engine is pure Go; it only pulls in OS concerns transitively through
    window and audio.
  - window is GLFW plus a small per-OS file picker. GLFW ships its own
    Win32 / X11+Wayland / Cocoa backends and picks one by GOOS, so it needs
    no build tags. The picker does: picker_dialog.go (windows || darwin,
    github.com/sqweek/dialog) and picker_unix.go (all other GOOS,
    zenity/kdialog via os/exec) — see section 12. window is the single seam
    for windowing, input and the file-open dialog: a non-GLFW port is a
    reimplementation of this one package's small API, nothing above it
    changes.
  - render/vulkan talks to the GPU through github.com/goki/vulkan and gets
    its surface + required instance extensions from window, so it is
    OS-agnostic Go. The one portability-specific bit is handled: the
    instance conditionally enables VK_KHR_portability_enumeration (+ the
    enumerate-portability create flag) and the device conditionally
    enables VK_KHR_portability_subset, each only when the loader/driver
    advertises it. That is exactly what MoltenVK on macOS needs and is
    completely inert on native Windows and Linux drivers (instance.go's
    hasInstanceExtension, device.go's deviceHasExtension). Shaders are
    committed as SPIR-V and embedded, so no per-OS shader step.

THE OS-SPECIFIC FILES — the entire list a porter recreates
  1. The audio/midi_*.go set — MUS/MIDI music, one type/method set
     (MusicPlayer, NewMusicPlayer, Play, Stop) with a per-OS body. The MUS
     timing loop and the track-switch discipline are shared (musicloop.go,
     all platforms); a backend supplies only send/silence/reset.
       - Windows: midi_windows.go is a dispatcher — try fluidsynth_windows.go
         (cgo LoadLibrary of libfluidsynth-*.dll + a bundled .sf2, rendered
         PULL-mode into the shared mixer), else winmm_windows.go (winmm.dll
         MIDI_MAPPER — the GS Wavetable synth on its own output, needs
         nothing). fluidsynth_stub_windows.go covers CGO_ENABLED=0.
       - midi_linux.go (//go:build linux): libfluidsynth via purego +
         a GM soundfont, runtime-loaded — no cgo, no build-time dep, pull
         mode into mixer.go. Errors out (music off, engine continues)
         when the lib or a .sf2 is missing.
       - midi_other.go (//go:build !windows && !linux): no-op stub, so
         macOS/BSD still build and run silent.
     purego cannot drive FluidSynth on Windows — its windows/amd64 fallback
     can't pass the double arguments fluid_settings_setnum needs — hence the
     cgo path there and purego only on Linux. A macOS port adds
     midi_darwin.go (AudioToolbox, or its own FluidSynth path) with the same
     symbols. Nothing outside package audio references the platform files
     directly — cmd/engine drives it through the exported surface
     (audio.Setup / audio.PlayLevelMusic / MusicPlayer.Stop, Game.OnLevel
     Change).
  2. The audio effect path is NOT build-tagged any more: audio.go +
     mixer.go are the one PrBoom-style software mixer for every platform
     (single 48 kHz S16 stereo oto stream, fixed voice pool, oldest-wins
     stealing, master gains, hard clip), shared with the pull-mode
     FluidSynth backends. oto itself is the only per-OS piece
     (CoreAudio / ALSA-PulseAudio / WASAPI), and it is cross-platform.
  3. cmd/engine/exitpause_windows.go  (//go:build windows via filename)
     "Hold the console open after a double-click launch" — GetConsoleProcess
     List. Cosmetic. exitpause_other.go (//go:build !windows) is already a
     no-op, correct for any OS where the engine is launched from a shell
     that outlives it. Recreate only if a given OS has an equivalent
     double-click-with-transient-console case worth handling.
  4. window/picker_dialog.go (//go:build windows || darwin) and
     window/picker_unix.go (//go:build !windows && !darwin). The startup
     "choose a WAD" dialog. picker_unix.go already covers every non-Apple
     Unix by driving zenity/qarma/matedialog/kdialog over os/exec — no code
     to recreate for a Linux/BSD port. Add a file here only for an OS whose
     native chooser is neither sqweek/dialog-supported nor one of those
     helpers. window.PickWADFile's $TPF_WAD / *.wad-argument path is
     OS-independent and always available as the no-dialog fallback.

  Those are the build-tagged files in the tree (grep `go:build`; plus the
  _windows.go / _other.go filename-tagged pairs). `golang.org/x/sys/windows`
  is used only by exitpause_windows.go; github.com/sqweek/dialog (and its
  w32 dep) only by picker_dialog.go — neither is in the Linux build graph.
  github.com/ebitengine/purego is used only by midi_linux.go (bind
  libfluidsynth without cgo); on Windows fluidsynth_windows.go binds it
  through cgo instead, so the Windows engine build needs CGO_ENABLED=1
  (which it already does for GLFW + Vulkan). Build the Windows exe with
  scripts/build-windows.ps1 (native) or scripts/build-windows.sh
  (cross-compile from Linux); both write bin/windows_engine.exe.

RUNTIME ASSUMPTIONS THAT ARE ALREADY CROSS-PLATFORM
  - All asset/config/IWAD lookup goes through filepath (not path) and
    findAssetDir / config's search walk — separators and parent-walk are
    OS-correct. The skybox and hi-res packs are read from disk, not
    embedded (sections 10, 11, 18), via the same findAssetDir logic.
  - Sound effects (audio.Device) use github.com/ebitengine/oto/v3, which
    is cross-platform (CoreAudio / ALSA-PulseAudio / WASAPI). Every
    platform runs one 48 kHz S16 stereo stream through the shared software
    mixer (mixer.go), which upsamples each DMX clip with linear
    interpolation itself rather than asking the OS mixer to resample from
    11 kHz — see section 13.
  - No syscall, no os-specific path constant, no hard-coded C:\ or drive
    letters, no CRLF assumptions in the loaders.

PER-OS BUILD PREREQUISITES
  cgo is required everywhere (GLFW + Vulkan bindings + oto). CGO_ENABLED=1
  and a C toolchain on PATH.
  - Windows: MinGW-w64 / UCRT64 (the reference build). Build with
    scripts/build-windows.ps1 -> bin/windows_engine.exe. vulkan-1.dll at
    runtime. Music defaults to the built-in GS Wavetable synth (nothing
    extra); for the better FluidSynth path (rendered into the same mixer as
    the sound effects), drop the FluidSynth release DLLs
    (libfluidsynth-3.dll + its dependencies) and a GM .sf2 next to the exe
    (or in a soundfonts/ folder, or point $TPF_SOUNDFONT at one).
  - Linux: gcc/clang; X11 (or Wayland) + GLFW's dev headers
    (libx11-dev, libxrandr-dev, libxcursor-dev, libxi-dev, libxinerama-dev,
    libgl1-mesa-dev or equivalent); ALSA dev headers for oto (libasound2-dev);
    a Vulkan ICD (mesa vulkan drivers / proprietary) and libvulkan. No GTK:
    the file picker calls zenity or kdialog at runtime (present on
    essentially every desktop; if absent, pass the WAD as a *.wad argument
    or in $TPF_WAD). Music is optional and runtime-only: libfluidsynth.so
    (libfluidsynth3) plus a GM soundfont (fluid-soundfont-gm or
    timgm6mb-soundfont); without them the game runs, just silent music.
    Verified on Linux Mint 22 / X11 with RADV on an AMD discrete GPU.
  - macOS: Xcode command-line tools; the Vulkan SDK / MoltenVK
    (libvulkan + the MoltenVK ICD). The portability extensions above are
    then picked up automatically.
  Recompiling shaders (rare — .spv is committed) additionally needs glslc
  from the Vulkan SDK on any OS.

STILL A NO-OP AFTER A BARE PORT (until file 1 above is done)
  MUS/MIDI music only, and only on the platforms with no backend yet
  (macOS/BSD — section 16). Windows and Linux have music. Everything else
  — rendering, input, sound effects, the file picker, the full game loop —
  works on first build.


22. PACKAGE launcher — THE PRE-GAME MENU
---------------------------------------
The screen shown before any game window opens: pick a WAD and a level, edit
every config.json setting, then Play. cmd/engine and cmd/isoengine both run
it in a loop with a play session (section 2); Quit (or closing its window)
is the only exit.

Decoupled from Doom by design (theme.go's package doc): no WAD assets, no
game fonts or palette — one public-domain 7x13 bitmap font (basicfont,
canvas.go), flat rectangles, a dark neutral slate palette (the `theme`
table, one place to re-skin). It reuses the engine's own presentation
stack, nothing new: a fixed 900x700 window (window.NewFixed) and a plain
vulkan.New(win, w, h, vsync=true, debug=false) blit renderer — "present
this RGBA8 CPU buffer", the same plain CPU-buffer path the level editor's
own GUI uses (section 25) — which is exactly what launcher.Canvas produces.
Both are torn down before the game's window stands up.

  launcher.Run(config.Load()) (run.go)
    - opens the window + blit renderer, builds Canvas / UI / Poller / Model
    - each frame: win.PollEvents -> Poller.Poll (one Input snapshot) ->
      ui.Begin -> Draw(ui, m) (screen.go — the whole UI in one function)
      -> ui.End (the open dropdown's overlay list, drawn last) ->
      renderer.DrawFrame(canvas.Img.Pix)
    - a "Browse..." click sets Model.BrowseRequested; run.go pops the
      native window.PickWADFile AFTER presenting that frame (a blocking OS
      dialog, not mid-draw)
    - loop exits on Model.Done (Play / Quit / window close). On Play:
      Cfg.Map / Cfg.WADPath are set and config.SaveMerge(Cfg, config
      .ResolvePath()) writes config.json, then Run returns a launcher
      .Result{WAD, WADPath, MapName, Config} and ok=true. Quit / close ->
      ok=false, Result zero, config.json untouched.

Model (model.go) is the whole live session state — one instance, one
goroutine, no locks. NewModel seeds it from the passed-in config; if
config's wadPath still resolves, PickWAD pre-loads it so re-launching drops
you back where you left off. PickWAD calls wad.LoadWithIWAD (parse + PWAD
merge, section 2), fills Maps, and picks a default level (the current one if
the new WAD still has it, else wad.PreferredStartMap). A failed pick leaves
any previous selection intact and only sets Model.Status.

UI (ui.go) is a small immediate-mode widget kit: Button, Checkbox, Slider /
IntSlider, Options (a dropdown whose option list is deferred and drawn on
top of everything by UI.End; scrolls past dropdownMaxRows = 8), TextField,
IntField, plus Hint (a one-line hover tooltip: queued by a row after its
widget draws, drawn on top by UI.End just before the dropdown overlay).
An open dropdown's overlay list also swallows the pointer: hover() returns
false for any widget while the mouse is inside ui.deferred.list, so a click
on an option can't also toggle the row it visually covers (an open
dropdown's list commonly extends down over the row below it).
Cross-frame state (which field has focus and its cursor, which dropdown is
open and its scroll, an in-progress IntField draft) lives in id-keyed maps,
so the ~35-row settings table needs no matching struct fields. Canvas
(canvas.go) is the CPU RGBA target: Fill / FillRect / StrokeRect / Text,
with a Clip stack (the settings panel clips to its viewport; font.Drawer
writes through a clippedRGBA wrapper).

Poller (input.go) turns window.Window's held-key/button state into per-
frame edges plus key-repeat (keyRepeatDelay 0.4 s, then keyRepeatRate
0.03 s) for text editing — a held Backspace must keep deleting, unlike the
game's "held W = keep walking". It reads window.MenuKey* (arrows,
Backspace/Delete/Home/End/Enter/Tab) and TakeTypedRaw (raw chars, no
game-key filtering). These MenuKey / raw-typed hooks are the launcher's
only additions to package window.

fields.go is the settings table: one `field` per config.Config key — an id,
a label, a one-line `hint` (its hover tooltip), a Section (which tab it
groups under), a widget `kind`, and a typed accessor closure straight into
a *config.Config (no reflection). fields_test.go asserts the table plus a
short explicit exclusion list (Map -> the top-bar level dropdown;
CartoonShading -> a top-bar checkbox; WADPath -> set programmatically;
ShowStatusBar -> the deprecated shim SaveMerge never writes; Music -> no
checkbox, the Music Volume slider is its on/off and run.go sets Music =
musicVolume > 0 on Play, with NewModel showing the slider at 0 when music
was off) accounts for every field on Config, so a field added later can't
silently go missing —
the same guard tools/genconfig's DefaultJSON has; other tests assert every
field has a hint and every Section has a tabTitles entry. The dropdown
option lists (resolutionOptions, hudStyleOptions, ...) pair
config.go's own accepted keyword constants with human labels, so the table
can't offer a value repaired() would reject.

screen.go: a fixed top bar (title, up to maxQuickChips = 5 WAD quick-pick
chips from launcher.ListWADs — every *.wad beside the assets.FindDir("wad")
directory — plus Browse..., the selected-WAD line, the Level dropdown, and
the Cartoon Shading checkbox), then the settings panel — a tab strip
(drawTabStrip: one button per Section, tabTitles for the short labels,
Model.ActiveTab the current one, switching resets the scroll) over just the
active tab's rows (layoutTab is the ONE layout computation, run once with
draw==nil to measure content height for scroll clamping and once to draw,
so the two can't drift; most tabs fit without scrolling). Hovering a row
shows its fields.go hint via ui.Hint. Then a bottom bar (Status line, Quit,
Play). Enter anywhere = Play unless a text field was focused when the frame
began (it consumes its own Enter to commit the edit); Play / Enter both go
through tryPlay's WAD+map validation.


23. cmd/isoengine — ISOMETRIC TOP-DOWN MODE
------------------------------------------
A standalone second executable: the exact same engine.Game simulation
(physics, collision, monster AI, sector specials, combat, pickups, the
35 Hz tic) rendered as a Vulkan-hardware top-down isometric view, with a
mouse-aim control scheme. It is not a mode switch inside cmd/engine — a
separate main() that shares the launcher and the play-session shape
(section 2/4) and nothing renders the first-person view.

Entry (main.go). `-camera orbit|fixed` picks the initial camera mode. run()
is cmd/engine's run() mirrored: audio.Setup once, then loop launcher.Run
(unmodified — some settings it edits, FOV / mouse sensitivity, are
first-person-only and simply unread here) and playSession; Escape / window
close returns to the launcher. TPF_WAD / a *.wad arg takes runHeadless.

playSession wiring on top of a normal engine.NewGame:
  - game.WorldBuilder = worldgeo.New(...) with SkipCeilings = true (a
    top-down camera would only ever see ceiling undersides); OnLevelChange
    re-applies SkipCeilings + Invalidate after engine/level.go rebuilds the
    builder for the next map.
  - game.ReplaceMovementSystem(engine.IsoMovementSystem{}) and
    game.ReplaceUseSystem(engine.IsoUseSystem{}) (section 14) — slots 0/1
    swapped in place, every other System unchanged.
  - the loop calls game.AdvanceSimulation(dt) itself (in game.Run's place),
    then game.SyncIsoWorldGeometry() (iso_render.go — the rebuild-static-
    geometry-on-change + sector-height-interpolation check renderFrame does
    for the hardware path, since this loop bypasses renderFrame), builds
    worldgeo geometry, collects this frame's sprites/voxels
    (game.CollectIsoWorldObjects — collectWorldObjects with sprite rotation
    taken from the camera azimuth via a virtual distant viewpoint, no
    "behind the view plane" cull since an orthographic camera has no
    behind), appends the player's own PLAY billboard (built here — the
    player mobj is never in Game.mobjs, section 14), draws the HUD onto
    raster's overlay plane (game.DrawHUD, config hudStyle / F1 the same as
    cmd/engine), and calls renderer.DrawIso(geo, cam, overlay, reveal).

Input each frame: WASD thrust is screen-relative to the camera azimuth
(Game.IsoCameraAzimuth), NOT the player's facing. The player faces and
fires toward the mouse: worldgeo.IsoUnprojectToGround gives the cursor's
ground point (Game.IsoAimX/Y), and nearestAimTarget snaps that onto a live
shootable mobj whose projected screen position (worldgeo.IsoProjectToScreen
over game.AimTargetPositions()) lands within aimSnapRadius = 40 px, so a
shot the crosshair is visually on connects (Game.IsoAimLocked, read by
weapons.go's spread). IsoMovementSystem also mirrors Camera.Angle onto
playerMobj.Angle every frame (not just per tic) so aim-then-click is exact.
IsoUseSystem activates the nearest special line within useRange by
proximity — a facing ray would point at whatever the mouse aims at, not the
switch the player walked up to.

Camera (camera.go, cameraController). A worldgeo.IsoCamera (camera_iso.go):
an orthographic camera looking at (TargetX/Y/Z — overwritten every frame to
follow the player) from Azimuth, tilted down by Elevation, with Zoom the
view half-height in map units. Elevation is pinned at IsoTrueElevation
(atan(1/sqrt2), the classic 2:1 isometric angle) for the controller's whole
life — it never tilts, only rotates and zooms. "orbit" mode: Left/Right
arrows rotate, right-mouse-drag rotates (left is fire), wheel zooms.
"fixed" mode: Left/Right step the 8 fixed 45-degree azimuths (Doom's own
sprite-rotation resolution). Tab toggles the two. IsoViewProj builds the
column-major mat4 (real 3D rotation, no pitch-shear hack — the camera is
genuinely tilted); IsoBasis is shared by the projection and the
screen->world unproject so they can't disagree.

GPU path (render/vulkan/isosetup.go + isoworld.go). vulkan.NewIso reuses
the shared instance/device/swapchain bootstrap, then builds its OWN
fixed-size offscreen colour+depth scene target, per-texture descriptor
cache, world + voxel pipelines (iso.vert/frag, isovoxel.vert/frag), and a
present stage that blits the scene to the swapchain letterboxed — its own
pool/sampler/pipeline rather than sharing worldResources', since hw and iso
are mutually exclusive per Renderer. DrawIso pushes IsoViewProj + a fixed
directional "sun" for shape + an ambient floor + the target size + a
player-occlusion fade radius as push constants. Seeing things behind walls
has three layers, all limited to the player's vicinity so a busy map's far
rooms stay clean:
  - Occluded-silhouette pass. After the normal sprite + voxel draws,
    recordIsoCommandBuffer re-draws just the moving things (never walls)
    with pipeSpriteReveal / pipeVoxelReveal — clones of the normal
    pipelines with GREATER depth compare, no depth write, alpha blend — so
    any monster/item/barrel a wall or a higher floor is hiding still shows
    as a flat ISO_REVEAL_TINT (warm gold) ghost. iso.frag gates it to
    within IsoRevealScreenRadius px of screen centre (fading over the outer
    third); recordIsoVoxels does the same by the model's projected NDC
    distance. IsoRevealAlpha = 0 disables the whole pass.
  - Wall shimmer. The Reveal UBO (up to maxIsoReveal = 64 screen positions,
    now built player-proximity-filtered in cmd/isoengine —
    isoRevealWorldRadius) still drives a dithered partial-discard of a wall
    between the camera and each nearby thing, but at a tight
    IsoRevealHaloRadius and a gentle cap — a "something's here" hint, not
    the peephole it used to punch.
  - playerFade: the original wider, up-to-35% dither around screen centre
    so a near wall never hides where the player is.
Voxel meshes upload lazily on first sight (syncIsoVoxelMeshes) rather than
warmed up front. Ground shadows (section 9) are not in this path.


24. HERETIC SUPPORT
------------------
Raven's Heretic (1994) shipped on this same 1993 engine, so its WADs load
and play on top of Doom / Doom II with a compatibility layer (engine/
heretic*.go, raster/heretichud.go, wad.WAD.IsHeretic). What is shared
unchanged: the map format, BSP, the renderer, and — because Heretic
inherited id's linedef table 1..98 verbatim — almost every line/sector
special. Ported: the full monster roster (data-driven, reusing the Doom
AI), all decorations, keyed doors, Heretic's eight weapons + six ammo
types, the ten inventory artifacts, the status bar, the sky, animated
liquids, sounds, music, and the voxel pack. Heretic is a playable game
here — what's NOT modelled is the Tome-of-Power *powered* weapon modes, a
real chicken-morph player state, and the wind/scrolling-current sectors.

Detection (wad.WAD.IsHeretic): the WAD carries a "MUS_E1M1" music lump
(Heretic's per-map prefix; Doom never uses MUS_) AND the Heretic-only menu
graphic M_HTIC. cmd/engine uses it to pick the voxel pack; the engine sets
Game.heretic, which switches on everything below.

  Things (engine/heretic.go's hereticThings, keyed by GZDoom's Heretic
  DoomEdNums). Heretic's doomednums mostly collide with different Doom
  things — doomednum 10 is a bloody corpse in Doom but Wand Crystal ammo in
  Heretic, 66 is a Revenant vs. a Gargoyle, 73 is a hanging torso vs. the
  green key — so spawnMapThings, when g.heretic, resolves a THING through
  the Heretic table FIRST and only falls through to doomedNumToType for
  what it doesn't cover (Heretic monsters, the 2001-2005 weapon slots).
  Each Heretic thing spawns as one MT_HERETIC mobj (a single shared
  template + spawn state S_HERETIC) with its sprite carried in
  Mobj.spriteOverride (Heretic sprites aren't in Doom's spriteNames table)
  and its box/flags set per-entry; mobjSpriteName resolves override-or-Doom
  at every render site. overrideFrames>1 gives a torch / brazier /
  chandelier a stateless sprite-cycle in mobjTick. Covered: the 3 keys
  (functional — see below), all ammo (mapped to a Doom ammo type),
  health/shield artifacts (mapped to a Doom heal / armour / power), the
  inert artifacts (egg, tome, wings, timebomb — collectible so they don't
  litter the floor but with no effect), and every static decoration
  (skull-hangs, serpent/wall torches, braziers, pillars, stalag*ites,
  moss, pods, the volcano, hanging corpses, key gizmos).

  Keys & doors. Heretic's keyed manual doors use the same special numbers
  as Doom (26/27/28 DR, 32/33/34 D1) with the same key groupings, so the
  only fix needed is that the Heretic key THINGS (doomednums 79/80/73 ->
  CKYY/AKYY/BKYY, granting Keys[0]/[1]/[2] via giveHeretic) actually spawn
  and can be picked up — before, they didn't, so every keyed door in the
  game was unopenable. Heretic's special 99 is NOT Doom's "SR blue-key
  blazing door": it is a passive scrolling wall texture (waterfalls /
  lavafalls), on one-sided untagged walls. Doom's activateLine would have
  flung every untagged sector open the instant the player pressed Space
  near one; for g.heretic, activateLine treats 99 as a no-op and
  spawnSpecials registers it as a wall scroller (like 48/85).

  Sky (engine.hereticSkyTexture, applied in ApplyMapInfo). Heretic ships
  only SKY1..SKY3 and picks by episode differently from Doom's SKY1..SKY4
  (E1->SKY1, E2->SKY2, E3->SKY3, E4/E5/E6 reuse SKY1/SKY3/SKY3); without
  this E4+ asked for a nonexistent SKY4 and drew the missing-texture
  checkerboard. Textures.DropHiresOverrides ("SKY1".."SKY3") removes the
  generated Doom sky PNGs (whose names collide), so Heretic's own fantasy
  skies show.

  HD textures (assets/textures/heretic/, section 11). cmd/engine's NewGame
  calls Textures.SetHeretic(true) for a Heretic IWAD, so a community Heretic
  HD pack imported by tools/importhereticpbr overrides every wall/flat it
  covers, ahead of every other override. Separate dir = its Doom-name
  collisions never reach a Doom session. Inert if the pack isn't installed.

  Liquids & animation. classifyFloorLiquid / worldgeo.liquidKindOfFlat and
  the builtinAnimDefs table gained Heretic's flat/texture families
  (FLTWAWA/FLTFLWW water, FLTLAVA lava, FLTSLUD sludge, FLATHUH; WATRWAL /
  LAVAFL walls) so Heretic liquids animate and get the water/lava shading.

  Torch lights + flames (engine/heretic.go). Every Heretic decoration is one
  MT_HERETIC mobj told apart only by spriteOverride, so the Doom decoLights
  table (keyed by mobjType) can't reach them and Heretic torches emitted no
  light. hereticDecoLights maps the sprite prefix — WTRH wall torch, SRTC
  serpent torch, KFR1 fire brazier, CHDL chandelier, VLCO volcano — to a
  warm fire-flicker decoLightDef PLUS a flameZ (the emitter sits up the wall
  / on the stand, not at mo.Height*0.72); hereticDecoLight(mo) returns both,
  and buildStaticLights falls back to it for an MT_HERETIC mobj decoLights
  misses. E1M1 goes 18 -> 39 static emitters.

  reikall's voxel models for these props are the bare bracket / dim ember —
  the flame is a separate model (TFULA.kvx) its DECORATE spawns as a child,
  which this engine doesn't run. LoadVoxelPack stashes TFULA under a
  reserved key (VoxelSet.HereticTorchFlame); when a torch/brazier voxelizes,
  the two world collectors (collectWorldObjects, CollectIsoWorldObjects)
  also emit that flame model on top via Game.hereticFlameFor — a
  worldgeo.VoxelInstance, FullBright, gently turning + bobbing, scaled and
  lifted per prep type (hereticTorchFlames), seated at the host model's
  visual top (baseZ + (ZPivot-0.5)*hostScale). The warm point light now sits
  at the same height, so the wall around a torch takes an orange cast.

  Monsters (engine/heretic_actors.go — hereticMonsters, keyed by Heretic
  DoomEdNum). Heretic mobjs behave like Doom's, so the ported Doom AI runs
  UNCHANGED: each monster is a hereticActorDef with GZDoom-style animation
  strings (parseHFrames) and a synthesized *MobjInfo whose SpawnState /
  SeeState / MeleeState / ... point at the S_HERETIC_* sentinels.
  setMobjState intercepts a sentinel and calls hSetPhase, so aLook /
  aChase / pDamageMobj / pKillMobj drive the data-driven FSM
  (hereticActorTick) transparently — aChase's "goto Melee" is just
  setMobjState(mo, mo.Info.MeleeState). The Mobj carries hact / hPhase /
  hFrameIdx / hFrameTic; mo.Tics is pinned -1 so the Doom state countdown
  stays out of it. Missiles are MT_HERETIC mobjs with MF_MISSILE + a per-
  shot hDamage (spawnHereticMissile / moveMissile); explodeMissile just
  removes them (no impact animation yet). Covered: Gargoyle + Fire
  Gargoyle, Golem + Ghost, Nitrogolem + Ghost, Undead Warrior + Ghost,
  Weredragon, Ophidian, Sabreclaw, Disciple; the Iron Lich, Maulotaur and
  D'Sparil are present but simplified (walk + one attack, big HP). Ghost
  variants are the base def + MF_SHADOW. Sound lump names (mumsit, kgtat1,
  ...) resolve case-insensitively against heretic.wad.

  Sounds (engine/heretic.go's hereticSfx, applied in loadSound when
  g.heretic). Every Doom "DS*" lump name the engine hard-codes (doors,
  switches, lifts, teleporters, pickups, player pain/death, and the still-
  Doom weapon fire) is remapped to Heretic's own prefix-less lump (DOROPN,
  SWITCH, ITEMUP, PLRPAI, GLDHIT, ...), so nothing falls silent.

  Music. audio.PlayLevelMusic tries "MUS_"+mapName alongside the Doom
  candidates, so Heretic's MUS_ExMy tracks resolve.

  Weapons (engine/heretic_weapons.go). PlayerStats.Ammo/MaxAmmo widened
  from [4] to [numAmmoTypes]=6 (4 flame orbs, 5 mace spheres). NewGame
  resetWeaponTables() restores a pristine Doom weapon set every session
  (also fixing a latent DEH leak through the launcher loop), then
  applyHereticWeapons() overwrites the 8 slots + weaponSlots in place:
  Staff/Gauntlets (melee) on slot 1, Elven Wand 2, Ethereal Crossbow 3,
  Dragon Claw 4, Hellstaff 5, Phoenix Rod 6, Firemace 7 — every non-melee
  slot carries a Heretic ProjectileDef (hFXWand FX01, hFXCrossbow FX03,
  hFXDragonClaw FX18, hFXHellstaff FX00, hFXPhoenix FX04+FX08, hFXMace
  FX02; the crossbow's is a 3-bolt spread via ProjectileDef.Shots/
  SpreadRad). The Wand deviates from vanilla on purpose: id's Gold Wand is
  hitscan, but "PUFF" isn't a lump here so a hitscan spark read as nothing
  leaving the wand — so it fires a real travelling FX01 bolt aimed straight
  down the crosshair (spawnProjectile uses Camera yaw+pitch), glowing warm
  via projectileLight's default. Fire mechanics reuse the Doom dispatch.
  Tome of Power: while pwTome > 0, beginFire swaps in each weapon's
  WeaponDef.Powered projectile (bigger, blast radius, the Firemace's one
  huge FX02-E death ball; the Wand's hFXWandP is a 5-bolt fan), and the
  Staff / Gauntlets hit ~2-4x with the Gauntlets leeching life.
  hereticPlayerStats() is the fresh spawn (staff + wand + 50 crystals).

  Weapon swap (config switchWeapons). NewGame reads cfg and picks the
  arsenal independently of g.heretic: hereticArsenal = g.heretic XOR
  switchWeapons. So a Doom level gets applyHereticWeapons() +
  hereticPlayerStats(), and a Heretic level keeps the pristine Doom table
  (resetWeaponTables already ran). Everything else keyed off g.heretic
  (sky, HUD, monsters, the hereticSfx sound remap) is untouched — only the
  guns change. The pickup THINGS grant by SLOT (giveWeapon(wpShotgun) etc.,
  and giveHeretic's hgWp* cases), so a Heretic crossbow THING in a Doom-
  weapon session hands you the Doom shotgun and vice versa with no extra
  wiring — and engine/switchweapons.go re-skins those THINGS to match: when
  g.swapWeapons, spawnMapThings calls swapDoomPickupSprite (a Doom
  weapon/ammo/backpack pickup mobj -> the equivalent Heretic sprite via
  weaponPickupSkins / ammoPickupSkins) and spawnHereticThing calls
  swapHereticPickupSprite (keyed by the hereticGift). Only the sprite
  changes (spriteOverride + the mobjTick frame cycler for the animated
  ones); the mobj type, collision, and touch handler are as before.
  Cross-game art/sound: cmd/engine finds the other IWAD (wad.OtherGameIWAD,
  which factors iwadSearchDirs out of resolveIWAD) and calls
  Textures.SetSpriteFallback — a sprite (or, via a lazily-built
  fallbackSpriteIndex in SpriteFrame, a whole sprite prefix) the played WAD
  lacks is pulled from that WAD and decoded through ITS palette, so a
  Heretic gun in Doom stays gold — plus Game.AltWAD (loadSound's fallback
  for a fire lump like BOWSHT / DSSHOTGN).

  Hit sparks (melee only, now the Wand travels). pLineAttack takes an hpuff
  sprite name: Doom uses MT_PUFF as authored, but "PUFF" / "BLUD" aren't
  lumps in heretic.wad, so a Heretic MELEE weapon (the Staff / Gauntlets,
  still hitscan-range) otherwise landed with no visible effect. spawnAttackPuff
  re-skins MT_PUFF to a real Heretic puff — PUF3 (the staff spark), PUF1
  (the green Gauntlets spark) — full-bright, cycling off hereticPuffFrames
  then self-removing via hExpireIn; spawnAttackBlood does the same to give
  MT_BLOOD Heretic's BLOD sprite. fireMelee passes PUF3 / PUF1.

  Artifacts (engine/heretic_arti.go). PlayerStats gains Inventory[10] +
  ArtiCurrent; the pickup routes an artifact THING to giveArtifact (stacks
  to 16). artifactSystem (a registered System) edge-detects Enter = use,
  [ / ] = cycle. Effects: Ring of Invincibility / Shadowsphere -> the Doom
  powers; Quartz Flask / Mystic Urn -> heal; Tome of Power -> pwTome (the
  powered weapon modes above, + a gold ExtraLight tint); Torch -> pwTorch (a
  brighter ExtraLight bump); Wings of Wrath -> pwFlight (free vertical
  movement in resolvePlayerZ); Time Bomb -> a fused pRadiusAttack
  (Game.timeBombs, ticked in runTic); Morph Ovum -> chickenize the aimed-at
  monster (swap its hact for the weak hChickenDef); Chaos Device ->
  teleport to the player-1 start.

  HUD (raster/heretichud.go). For a Heretic game g.drawHUD routes BOTH
  in-game styles to a Heretic renderer: "doom" -> DrawHereticStatusBar
  (BARBACK, the gargoyle end pieces, the health chain + sliding LIFEGEM, the
  IN / SMALLIN number fonts for health / armour / ready ammo, the
  YKEYICON/GKEYICON/BKEYICON key icons, the artifact box + selected
  artifact icon + count from HUDStats.Arti / ArtiCount); "quake2" ->
  DrawHereticQuakeHUD, the same minimal-corners idea as DrawQuakeHUD (big
  health bottom-left, big ready ammo bottom-right, no status-bar chrome) but
  with those Heretic lumps — health/armour in "IN", the six ammo pickup
  sprites (hereticAmmoIcons), the shield icon, and the key column with the
  selected artifact box stacked above it on the right edge (Quake II has no
  inventory, and the bottom centre is the weapon's). Ghost monsters
  (MF_SHADOW) are drawn at 1/3 sector light — no fuzz distortion, but they
  read as shadowy.

  Bosses (engine/heretic_actors.go). The Iron Lich / Maulotaur / D'Sparil
  each carry a hereticActorDef.bossMissiles slice; the "boss" frame action
  (hDoBossAttack) picks one at random per attack (or the melee if the
  target is close), giving the Lich its ice-ball / slow-ball / fire-column,
  the Maulotaur its hammer + fireball + floor-fire, and D'Sparil a
  fast/slow fireball. Behaviour and HP only — the Lich's whirlwind, the
  Maulotaur's charge, and D'Sparil's two-phase serpent-then-mage fight are
  not modelled.

  Wind (engine/specials.go hereticWindThrust). Heretic sector specials
  20-39 (east/north/south/west, five strength slots each) add a per-tic
  push to the player's velocity in playerInSpecialSector, airborne
  included. Specials 40-51 (mobj-only wind) aren't modelled.

  Monster-projectile impacts. explodeMissile freezes an MT_HERETIC missile
  in place, swaps to its hMissileDef.deathSprite (defaulting to a short
  replay of the flight sprite) and removes it after the animation
  (Mobj.hExpireIn, decremented in mobjTick).

  Voxels (config voxels). cmd/engine and cmd/isoengine pick
  assets/voxel/reikallhereticvoxels.pk3 when w.IsHeretic(). Two loader
  fixes were needed: the pack's def lump is named "VOXELDEF" (no ".txt"),
  and it uses bare 4-letter sprite keys ("akyy" = every frame of AKYY) that
  parseVoxeldef now accepts (stored as "<sprite>*", resolved by
  VoxelSet.Model's whole-sprite fallback). ~60 sprite frames map directly
  from its VOXELDEF; the rest of the pack's models are wired through its
  DECORATE, which this engine doesn't parse, so LoadVoxelPack detects the
  pack (its "akyy*" key) and hand-fills ~41 more sprite->KVX pairings
  (hereticVoxelAlias — ammo crystals, braziers, torches, pillars,
  stalag*ites, moss, chandeliers, key gizmos, hanging skulls, the six
  weapon pickups). Combined VOXELDEF + aliases cover ~98 KVX models / 101
  sprite frames. Anything still unmapped falls back to the (correct)
  Heretic sprite. reikall's pack has NO monster models — every Heretic
  monster stays a billboard sprite (this is the pack, not a bug); it
  voxelizes items, ammo, keys, weapons, and decorations only.

  Confirmed working on the hardware path: the GPU voxel pipeline
  (render/vulkan/worldvoxel.go recordVoxels) draws every collected
  instance — a live E1M1 frame is ~116 instances / 116 vkCmdDraw, all
  cache-resident. Two one-shot log lines make it visible at a glance:
  engine's "[hw] map objects this frame — N voxel instance(s), M sprite(s)"
  (engine/game.go) and vulkan's "voxel models — drew N of M instance(s) ...
  K model(s) resident".

Not done: a real chicken-morph PLAYER state (single-player Heretic has no
way to trigger one — the Morph Ovum chickens a monster instead); the
bosses' signature moves (Lich whirlwind, Maulotaur charge, D'Sparil's
two-phase fight); Heretic's MAPINFO / episode-end story screens; and the
Tome-of-Power counter on the HUD. Also the DECORATE-only voxels the pack
can't hand-alias, and monster voxels (the pack ships none).


25. cmd/editor — THE LEVEL EDITOR
----------------------------------
A dual-view map editor: a 2D top-down view on the left, and the same
hardware (GPU-geometry) renderer the game itself uses rendering the map
live on the right, so an edit shows up in 3D immediately. See
EDITOR_MANUAL.txt
(repo root) for the user-facing how-to; this section is the shape of the
code underneath it. A separate executable from cmd/engine — it shares no
process state, only packages — built on a NEW immediate-mode UI kit
(imkit/) rather than launcher/'s, since the editor's panels (a draggable
splitter, tabs, a thumbnail grid, drag-and-drop, popup menus) go well
beyond what the settings-screen kit offers; the two kits are siblings, not
yet unified.

editor.Run(wadPath, startNew, fullscreen) (app.go) owns the whole session:
  - resolveWAD picks a WAD (the argument, or the first *.wad WITH AT LEAST
    ONE MAP under wad/Game WADs/, wad/, or assets/, walked in that order —
    skipping a map-less WAD, e.g. a pure texture pack, that would otherwise
    load fine and then fail with "no maps"); LoadBank aggregates textures
    (see below); NewDoc loads the WAD's first map, or NewEmptyDoc builds a
    fresh one (-new / File > New Level — a real, immediately-playable
    512x512 room + a player start, textured from whatever names the asset
    set actually has, never a name that doesn't exist there).
  - App.openWindow(fullscreen) creates the window (window.NewFixed at
    1600x900, or window.New(0,0,title,true) — borderless, the monitor's
    own mode, the exact mechanism cmd/engine's fullscreen uses) and its
    vulkan.NewWorld renderer (section 9's hardware path — App.blit is a
    render/vulkan.Renderer built for GPU-geometry, not the plain CPU-buffer
    blit the launcher's own Canvas uses; see view3d below for why). F11 /
    View > Toggle Fullscreen calls it again later — from App.pending, never
    mid-frame — tearing down the old win+blit and creating new ones;
    imkit.Canvas.Resize keeps the SAME *Canvas (so imkit.UI and every
    widget's cross-frame id-keyed state survive the switch untouched) and
    the 2D/3D split position rescales proportionally to the new width.
    cmd/editor/main.go's init() calls runtime.LockOSThread(), matching
    cmd/engine/cmd/isoengine — every GLFW call has to stay on the thread
    that called glfw.Init(), and editor is its own binary so it needs its
    own pin.
  - The frame loop mirrors launcher.Run's shape: PollEvents -> Poller.Poll
    -> ui.Begin -> App.frame (menu bar, the VSplit, the three panes, the
    status bar) -> ui.End -> blit.DrawWorld(v3.geom, v3.wc, cv.W, cv.H,
    cv.Img.Pix, nil) (view3d's doc comment explains why DrawWorld, not
    DrawFrame, presents the WHOLE editor UI); a deferred App.pending
    closure runs after present (Play, Save, New Level, the fullscreen
    toggle — anything that shouldn't mutate state mid-draw); Doc.
    RebuildIfDirty runs last, picking up any geometry edit made this frame.

Bank (assets.go) is the editor's merged asset set: wad.Merge across the
WAD being edited plus every *.wad found (recursively) under the same three
directories resolveWAD searches, one assets.Textures over the result, and
the browsers' name lists — wad.WallTextureNames (TEXTURE1/2) and
wad.FlatNames (between the F_START/FF_START.. _END markers, sub-section
markers themselves excluded) — both new wad/enumerate.go additions, since
the engine itself only ever resolves a texture by name, never lists them.
WallThumb/FlatThumb cache a decoded *image.RGBA per name for the thumbnail
grid.

Doc (doc.go) is the map being edited: it mutates a *wad.Level's slices
directly (Vertexes/Linedefs/Sidedefs/Sectors/Things — no separate edit
model yet, see EDITOR_MANUAL.txt's Limitations), plus a `selection` (one
map[int]bool per element kind). The 3D view never reads that Level
directly — Doc.render is a SEPARATE wad.Level (a shallow copy with its own
Vertexes/Segs/Subsectors) that Doc.rebuildTree fills from nodebuild.Build,
so the node builder's own bookkeeping (the split-point vertices it has to
add when a partition cuts a wall) can never leak into, or get clobbered by,
the geometry you're actually editing — an earlier version appended those
straight onto Level.Vertexes and trimmed them back off before every
rebuild by a remembered count, which a future geometry edit would have
silently invalidated. rebuildTree runs nodebuild.Build after any edit that
calls Doc.markDirty (RebuildIfDirty is the once-a-frame, no-op-if-clean
check); on failure it falls back to the WAD's own shipped NODES if the map
still has them, else keeps the last good tree and records the error for
the status bar and the 3D pane's placeholder text.

nodebuild (package nodebuild, used only by the editor and its tests) is a
classic recursive BSP builder producing the exact bsp.Node/InnerNode/Leaf +
wad.Seg/Subsector types bsp.Build reads from a real NODES lump, so nothing
downstream (the renderer, bsp.SubsectorPolygons, bsp.PointSector) can tell
the difference. Each one/two-sided linedef becomes one or two segs; at each
step the seg whose line best divides the remaining set (fewest splits,
most balanced) becomes the partition, straddling segs are split at the
exact float intersection (rounded to integer only when a vertex is finally
emitted), and a set no seg's line can divide is a convex leaf. classify's
on-partition epsilon is deliberately tiny (0.05 world units) — the build
works in exact floats, so a genuine crossing is never that close, and a
looser epsilon was found (via a 100%-vs-shipped-NODES point-in-sector test
across 9 maps) to misread a shallow crossing as "entirely on one side" and
drop that wall from the other subtree: a leak that silently merged two
sectors' space into one convex cell. nodebuild.Reject is always all-zero
(valid — no sight-check shortcut, not incorrect) and nodebuild.Blockmap
walks each linedef in short steps marking every 128-unit cell it crosses;
neither is held to matching what a particular vanilla builder or another
port's own tool would produce (see EDITOR_MANUAL.txt's Limitations) — the
target is this engine's own loader.

view2d (view2d.go) is the left pane: pan (middle-drag) and zoom-to-cursor
in world space (camX/camY/zoom map to screen through w2s/s2w), a grid whose
line spacing self-hides once screen-thin, and four selection Modes
(Vertices/Linedefs/Sectors/Things — number keys 1-4 or the toolbar) each
with their own nearest-element hit test (nearestVert/nearestLine/
nearestThing by screen-pixel distance; Sectors by bsp.PointSectorIndex on
Doc.render). Selecting anything calls the onPick callback App.Run wires to
view3d.FocusOn (below). The DRAW tool (G, or the toolbar button) collects
grid/vertex-snapped clicks into a draft polyline (view2d.snap prefers an
existing vertex within ~10 screen px, else the grid) and, on a click back
near the first point, commitRoom turns it into a brand new sector: fresh
vertices, one-sided linedefs all the way around, textured from the panel's
current Walls/Flats selection. Doom's front sidedef is the RIGHT side of a
linedef's start->end direction, so a one-sided room's walls face inward
only if the loop winds clockwise in map space (y-up); commitRoom's
polyArea check reverses the draft if it doesn't (this exact winding was
backwards in an early version of both commitRoom and NewEmptyDoc — every
wall backface-culled from inside the room it bounded, and the 3D view
rendered solid black; TestCommitRoomFacesInward / TestNewEmptyDoc
BuildsAndFacesInward in editor/doc_test.go check it the same way
the GPU-geometry builder's own backface cull does, by cross product against the
room's centre). Drag-and-drop (imkit.DragSource/DropTarget) is how a
texture/flat/thing actually gets onto the map — see panel below;
view2d.drawDropHover outlines the live drop target while a drag is in
flight. A click on the pane's own
top-left toolbar strip (y < rect.Y+34) is excluded from both selection and
the draw tool, so choosing a mode or hitting DRAW can't also select or
place a vertex on whatever geometry happens to sit under the button.

view3d (view3d.go) is a live 3D preview rendered through the SAME hardware
(GPU-geometry) path the game itself uses (render/worldgeo + render/vulkan's
DrawWorld) rather than a separate CPU renderer — App's blit renderer is a
vulkan.NewWorld, not the vanilla vulkan.New the rest of the editor's 2D UI
used to use exclusively. Since the editor composites its whole UI as one
CPU-drawn 2D plane (imkit.Canvas), the pane works the same way the game's
own weapon/HUD overlay does, just inverted: view3d.draw cuts a fully
transparent hole (Canvas.ClearRect) in the 2D canvas over the pane's rect,
and App.Run's single per-frame DrawWorld call paints the GPU-rendered world
underneath the WHOLE canvas — invisible everywhere the 2D canvas stays
opaque (menus, the 2D map view, panels), showing through only there. The
camera's FOV is still computed for the full window (DrawWorld has no
notion of a sub-viewport), so the pane shows an undistorted but more
"zoomed in" crop of that projection rather than one framed for its own
aspect ratio. view3d keeps a worldgeo.Builder, rebuilt only when Doc.tree
actually changes (an edit), and a free-fly raster.Camera: RMB-drag looks
(WASD/Q/E move — see the key table below), always built from
Doc.RenderLevel() against Doc.tree, whatever it currently is.
FocusOn(x, y, floorZ) — the 2D selection's "jump the 3D view there" — does
not teleport: it computes a point back along the camera's existing bearing
to the target (so it approaches from roughly where it already was, not
through a wall on the far side), stores it as a glide{} target alongside
the current pose as the start, and stepGlide eases position and angle to
it over ~0.3s (smoothstep). Moving the camera yourself (WASD, or a
right-drag look) cancels an in-progress glide.

panel (panel.go, things.go) is the right-docked tabbed browser: Walls and
Flats are both imkit.ThumbGrid over Bank's name lists with a filter box —
clicking a thumbnail sets it as DRAW's current texture, dragging one onto
a linedef (Walls) or into a sector (Flats, via Doc.SetLineTexture /
SetSectorFlat) textures it directly. Things is a filtered, categorised
list built from a hand-maintained thingDefs table (doomednum, name,
category, sprite prefix — Doom/Doom II only so far, no engine.MobjInfo
cross-check or Heretic types yet) whose rows are themselves drag sources
(thingPayload{num}); dropping one calls Doc.AddThing at the snapped drop
point. Info is a plain read-out of the map's element counts and the
current selection size — no per-element inspector fields yet (heights,
light, special/tag, angle — see EDITOR_MANUAL.txt's Limitations).

Saving (save.go): Doc.SavePWAD runs nodebuild.Build fresh (independent of
the live Doc.render used for preview) and writes a single-map PWAD via the
new wad/write.go — EncodeVertexes/Linedefs/Sidedefs/Sectors/Things/Segs/
Subsectors/Nodes (each the exact byte-for-byte inverse of wad/level.go's
own decoders) plus wad.WritePWAD (header + directory + lump bytes) and
wad.MapMarkerLumps (the marker + the 11-lump block in loader order).
File > Save map as PWAD (Ctrl+S) writes "<wad>_<map>.wad" next to the
source; File > Play this map (F5) does the same to a temp file and execs
the engine binary on it (bin/linux_engine, bin/windows_engine.exe, or
"engine" on PATH) so a level can be played without leaving the editor.

Keys and controls:
  1 / 2 / 3 / 4          2D mode: Vertices / Linedefs / Sectors / Things
  G                      toggle the DRAW tool; Esc cancels a room in progress
  left-click             (select mode) pick the nearest element, or clear;
                        (draw mode) place a snapped point / close the loop
  scroll wheel           2D: zoom to cursor.  panel: scroll the list
  middle-drag            2D: pan
  [ / ]                  halve / double the 2D grid spacing
  Home                   frame the whole map in the 2D view
  drag a thumbnail/row    onto a linedef (wall), a sector (flat), or
                        anywhere on the map (a thing) to drop it there
  RMB-drag (3D pane)     look around
  W / A / S / D          3D: move forward / strafe-left / back / strafe-right
  Q / E                  3D: move down / up
  Shift (3D pane)        move faster
  F11                    toggle fullscreen
  Ctrl+N                 new level        Ctrl+R   reload the current map
  Ctrl+S                 save as PWAD     F5       play this map
  Ctrl+Q                 quit
